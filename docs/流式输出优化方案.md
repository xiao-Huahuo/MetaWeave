# 流式输出优化方案

本文记录 MetaWeave 主 Agent 长文、代码流式输出卡顿的排查与修复经验，供后续开发、性能复查和回归验收使用。整理日期：2026-10-03。

核心做法是减少每个 token 引发的额外工作：按帧聚合正文更新，缩小响应式依赖范围，保留已经显示的 DOM 和已排版的文本前缀，合并滚动布局读取。Markdown、高亮、链接、内容净化及终态内容完整性仍由现有链路负责。

## 1. 从症状判断排查方向

这次用户反馈：思考条输出正常，主 Agent 开始输出正文后文字明显卡顿，长文和代码尤其严重，连“正在思考”的扫描发光也一起变卡。修复后，用户确认实际使用中的卡顿已消失。

思考摘要较短，正文需要执行 Markdown 解析、高亮、DOM 更新和排版。同一阶段里，文字、动画及输入响应同时变慢，是检查浏览器主线程工作量的重要线索。底部“正在思考”使用 `background-position` 扫光，需要持续绘制；思考条自身的扫光使用 `transform`，两者应分别观察。

排查时分开测量三个阶段：服务端事件何时到达、草稿何时提交到状态、状态何时出现在界面。若事件到达连续而界面更新停顿，应继续检查状态和渲染链路；若原始事件本身很大或间隔很长，则检查提供商、后端及代理。不同问题需要各自的证据。

## 2. 本次确认的根因与修复

| 根因 | 可复现证据 | 修复 |
| --- | --- | --- |
| 首字延迟 metadata 被后续正文 token 反复重建 | 相同字段值对应的 metadata 引用持续变化，产生帧缓冲之外的状态更新 | 仅在派生值发生变化时替换 metadata |
| 窗口同步的 Pinia 深订阅遍历历史与模型上下文 | 修改当前正文时，历史消息和上下文中的探针 getter 被访问 | 使用浅监听，观察状态引用、消息数量及附件数量 |
| 开发环境 DevTools 也注册了同步深订阅 | 模拟该订阅后，正文增长仍触发大模型请求快照的深遍历 | 对整体替换的快照数组及最新请求消息数组使用 `markRaw` |
| 历史气泡接收新的空数组、空对象 props | 更新最后一条正文时，旧用户消息和旧回答的组件更新钩子也执行 | 复用稳定的空引用，让 Vue 跳过无变化的历史组件 |
| 活跃 Markdown 段落或代码块每次整块替换 | 追加文字后，原来的段落、代码、列表和表格节点被移除 | 对净化后的 DOM 进行增量修补，保留匹配的已有节点 |
| 超长原生 Text 节点反复增长 | 即使保留段落元素，长单段正文仍有显著排版成本 | 保留较长文本前缀，通过小后缀节点追加文字 |
| 自动滚动在正文更新后立即读取布局 | 同一帧内两次正文变化触发两次高度读取和滚动 | 按动画帧合并，执行前检查底部跟随状态和用户滚动意图 |

实现入口见 [chat.ts](../editor/src/stores/chat.ts)、[MessageList.vue](../editor/src/components/editor_workspace/agent_chat/MessageList.vue)、[MarkdownContent.vue](../editor/src/components/editor_workspace/agent_chat/MarkdownContent.vue) 和 [patchMarkdownDom.ts](../editor/src/components/editor_workspace/agent_chat/patchMarkdownDom.ts)。

## 3. 状态更新与窗口同步

### 3.1 高频正文先进入草稿，再按帧提交

正文和 thinking 使用各自的非响应式草稿 Map，按照消息归属聚合增量，再通过 `requestAnimationFrame` 提交。消息归属需要明确，避免节点切换后把上一段草稿写入下一条消息。

节点切换、权威完整响应、完成、异常和取消等边界应强制冲刷草稿。可见界面的正常增长由帧调度合并；边界处理负责确保最后一小段文字进入正确的消息。

`requestAnimationFrame` 只合并提交时机。Markdown 解析、状态依赖和排版仍可能占用主线程，结构变化和强制冲刷也可能产生额外更新，因此它不保证每帧恰好一次渲染或恒定 60fps。

### 3.2 固定信息保持稳定

首字延迟一旦确定，后续正文 token 应复用已有 metadata。相同的派生字段值无需重新创建对象；新的工具状态、引用来源等有效 metadata 仍按现有业务逻辑更新。

检查 token 处理代码时，除了正文字符串，也要查看是否重复赋值空 `tool_calls`、空 trace、相同统计信息或相同对象。小字段的重复赋值也可能使较大的响应式依赖重新执行。

### 3.3 浅监听需要明确观察范围

窗口同步观察 `chatMetaState` 中的引用与标量，以及消息、附件数量。正文增长使用有顺序号的增量事件；流式开始、结束及同步请求等边界继续发送完整快照。

浅监听的正确性依赖明确的状态更新方式。新增需要同步的字段时，应检查它是否进入 metadata 状态，以及它通过替换引用、改变数量还是修改内部字段来更新。

同步监听放在由 store 持有的独立 `effectScope` 中，组件卸载不会提前停止会话同步；`store.$dispose()` 负责停止该 scope 并移除对应注册。这个清理路径不能自动推导为所有应用级销毁入口都已覆盖。

### 3.4 不可变快照显式跳过深遍历

模型请求快照按整组替换，最新请求的消息数组也通过新的数组副本更新。两者可以使用 `markRaw`，使 Vue 深遍历跳过这些大载荷，同时保留数组替换带来的界面更新。

`markRaw` 不会冻结对象。使用它之后，内部字段修改不会自动产生原有的深响应式通知，所以只适用于当前这种整体替换的快照。流式、历史恢复及远端状态接收统一经过 `setContextSnapshots`，确保处理方式一致。

开发环境还需检查框架或调试器自动安装的订阅。本次发现 DevTools 的同步深订阅后，保留了调试功能，通过缩小需要遍历的数据范围降低成本。

## 4. Markdown 与 DOM 更新

当前主要显示流程如下。SSE 解码器还会在处理一定数量的事件后主动让出执行机会，供定时器、输入及渲染继续运行。

```mermaid
flowchart LR
    A["SSE 接收与解码"] --> B["按消息归属聚合草稿"]
    B --> C["动画帧提交状态"]
    C --> D["活跃 Markdown 解析、高亮与净化"]
    D --> E["保留已有 DOM，修补变化"]
    E --> F["合并自动滚动与绘制"]
```

### 4.1 保留稳定块和活跃块中的稳定节点

已经完成的 Markdown 块沿用原有 DOM。正在增长的尾部仍经过现有解析器、高亮器、数学渲染及 DOMPurify；生成安全节点后，由 `patchMarkdownDom` 修补当前尾部。

同类型节点可复用，变化的属性、文字及子节点才更新；类型改变时替换对应节点，删除已经无效的旧节点。未闭合的强调、链接等语法在后续输入中完成时，允许解析结果重新解释相应内容。

终态继续完整解析一次，以校正需要全文上下文的 Markdown 语义。增量 DOM 更新必须与这条终态校正路径一起验证。

DOM 修补函数接收已经净化的节点，本身不承担 HTML 安全检查。DOMPurify 必须保留在它之前；复制按钮、链接图标等可信增强也要保留原来的交互与生命周期。

### 4.2 长文本前缀保持稳定，小后缀继续增长

保留 `<p>` 元素后，如果其中唯一的 Text 节点一直增长，浏览器仍可能重新处理很长的文本前缀。当前实现把通常可继续修改的末尾 Text 控制在 1,024 个字符以内；超出时追加新的 Text 节点，并在下一次修补时按连续文本组比较内容。

这样保留了已经显示的长前缀，同时维持原来的文本顺序和格式。这个阈值约束可增长的小后缀，不代表初次大块输入或单个大 delta 会被自动切成所有节点都小于 1,024 字符。

节点稳定也不等于整条链路变为 O(delta)：活跃尾部仍会解析，字符串比较和 DOM 比较仍有成本。若今后输出规模继续增长，应根据新的性能记录确定下一处瓶颈。

### 4.3 图标成功与失败状态都要保留

链接图标加载失败后会移除图片、留下 fallback。只通过现存图片判断资源是否相同，会在下一批正文更新时重建图标并再次请求同一资源。

当前 [markdownLinkIcons.ts](../editor/src/components/editor_workspace/agent_chat/markdownLinkIcons.ts) 在图标容器上记录资源标识。DOM 修补对同一资源保留已有容器、加载状态、fallback 和绑定的事件；资源变化时替换容器，让新事件回调继续绑定正确的节点。

## 5. 滚动、解码与取消

### 5.1 自动滚动每帧合并，并服从用户意图

正文更新后安排一个待执行的滚动帧。执行时读取高度，并重新检查用户是否仍跟随底部、是否已经产生上翻意图。待执行期间收到上翻操作时，旧滚动不能把用户拉回底部；回到底部后恢复自动跟随。

卸载时取消待执行帧和延迟任务。此机制仍需要读取布局，但减少了同一帧内重复的同步读取。

### 5.2 大块 SSE 到达时主动让出执行机会

[client.ts](../editor/src/api/client.ts) 的 `streamLines` 每处理 16 个事件主动让出执行机会，优先使用 `scheduler.yield()`，不可用时使用 `setTimeout(0)`。这可以避免网络缓冲中的大量事件在一个连续任务里被耗尽。

事件数量属于公平调度策略，不是固定的毫秒预算。单个大事件仍可能昂贵，需要分别测量解析、状态提交与渲染的成本。

### 5.3 取消回调与监听器明确回收

Fetch 取消可能先把 readable body 设为错误状态，再执行 reader 的取消回调。此时 `reader.cancel()` 返回的 Promise 也可能拒绝；未处理它会留下 `unhandled rejection`。

取消回调处理这类清理拒绝，正常读取路径继续负责传播有效错误；`finally` 移除 abort listener 并释放 reader lock。界面中断还需冲刷已经进入草稿的增量。

中断验收检查的是客户端已经接收、接受的文字，不包括尚未消费的网络缓冲或提供商尚未发送的内容。浏览器 reader 回收也不能单独证明服务端任务或提供商任务已终止。

## 6. 可复用的验证方法

先建立会失败的回归，再修改共享路径，并在实际界面复测：

1. 在旧历史消息、上下文中放置 getter 探针，确认只更新当前正文时是否访问它们。
2. 检查固定 metadata 的引用是否稳定；观察旧气泡的组件更新次数。
3. 保存已显示段落、代码、列表行和表格行的节点引用，追加内容后确认前缀节点仍然存在。
4. 验证未闭合行内语法的修正、图标加载成功与失败状态，以及不安全属性的净化。
5. 检查同一帧内滚动是否合并，上翻是否取消跟随，返回底部后是否恢复。
6. 用真实页面、生产解码器和组件运行受控 SSE 回放，测量 RAF 帧间隔、Long Task、文字更新次数、扫光状态变化和按钮响应。
7. 单独验证中断时的草稿冲刷、文字完整性、页面错误及监听器释放。

界面回放应包括长单段正文、长代码、无空段分隔的列表与表格，并保留足够大的历史上下文快照。短段落测得流畅，不能证明持续增长的活跃块也流畅。

测试按文件、单 worker 串行执行。回放定时器、观察器和服务均由测试拥有并回收，输出目录使用独立路径，避免与其他任务互相清理。纯文档更新只需检查编码、内容与链接。

### 本轮验收结果

Chromium，1440×960，真实 Vite 开发页面；受控 SSE 回放包含 6 份大模型请求快照和首字延迟 metadata。统计稳定增量阶段，初次大块装载与终态完整解析不计入以下帧统计。

| 案例 | P95 帧间隔 | 最大帧间隔 | 最长 Long Task | 侧栏响应 |
| --- | ---: | ---: | ---: | ---: |
| 56,000 字符单段正文 | 33.4ms | 66.7ms | 53ms | 21.1ms |
| 280 行 Python 代码 | 16.8ms | 33.4ms | 未记录到 | 11.3ms |
| 330 项列表 | 16.7ms | 16.8ms | 未记录到 | 14.3ms |
| 330 行表格 | 16.8ms | 16.8ms | 未记录到 | 15.5ms |

已有前缀 DOM 替换次数均为 0；两种扫光各采到 12–17 个不同状态，输出期间可输入并打开侧栏。70 项定向回归、5 项界面冒烟及生产构建通过。

这些数据来自修复验收时的受控回放，未连接外部模型提供商，也不代表所有设备和输出长度下的恒定帧率。超长单段仍有排版成本；全仓类型检查另有其他文件的既有错误。
