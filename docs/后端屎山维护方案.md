# MetaWeave 后端屎山维护方案

> 文件功能：定义 MetaWeave 后端结构重构的范围、目标架构、实施顺序、验收清单与证据标准。
>
> 使用方法：实施者必须按照本文的任务编号逐项执行；每完成一个阶段，都要提交对应的自动化测试结果、接口契约对比、实际界面冒烟记录和 README 更新。本文不授权修改业务逻辑、接口语义或用户数据。

## 1. 目标

本次维护只处理后端代码的组织、依赖方向、启动装配、数据库基础设施和协议适配边界。目标是降低巨型文件、全局状态、重复协议实现和散落数据库初始化带来的维护风险，同时保持现有业务行为完全不变。

本方案对应 `TODO.md` 中“维护后端的屎山代码”条目。所有实施项使用稳定编号，避免 TODO 行号变化后失去对应关系。

### 1.1 必须实现

- MW-BE-01：拆解 `agent_service/agent_core/agent_core.py`。
- MW-BE-02：拆解根目录 `main.py`。
- MW-BE-03：使用 `ApplicationServices` 取代 REST 依赖模块中的零散全局 Service 实例。
- MW-BE-04：拆解 `knowledge_library_service.py`。
- MW-BE-05：拆解 `knowledge_graph_service.py`。

### 1.2 明确不做

- 不新增、删除或改变任何业务功能。
- 不改变 REST 路径、HTTP 方法、参数、状态码和响应字段。
- 不改变 `.proto` 中的 service、RPC、message、field number 和字段语义。
- 不改变 Agent 流式事件的事件名、顺序、字段、结束条件和错误语义。
- 不改变数据库业务字段语义、默认值、数据内容和用户可见行为。
- 不顺便修改前端视觉、交互、文案或状态管理。
- `agent_service/core/agent_config.py` 在本任务中的 Git diff 必须为零；如目录迁移导致它必须修改，实施者必须暂停并先征得用户同意。
- 不以重构为理由升级无关依赖、修改 Docker 配置或更换技术栈。
- 不复制已有业务实现；移动后的模块必须复用现有 Service、节点、repository 或 RAG 组件。

## 2. 总体约束

### 2.1 业务不变原则

“业务逻辑不变”必须由契约和实际运行结果证明，不能只依赖代码审查结论。任何阶段只要出现以下任一变化，即视为验收失败：

- 现有测试从通过变为失败。
- OpenAPI 契约产生未经说明的差异。
- gRPC descriptor 或 RPC 行为产生未经说明的差异。
- 同一固定输入产生不同类型、不同字段或不同顺序的 Agent 事件。
- 旧数据库无法升级、记录丢失或关键字段变化。
- 前端现有操作出现 404、5xx、无限加载、状态不刷新或数据丢失。

若现有测试本身依赖私有模块路径，允许只修改测试 import；不得趁机改变测试断言所表达的业务行为。

### 2.2 渐进迁移原则

- 每个阶段必须能够独立合并和独立回滚。
- 先建立行为基线，再移动代码。
- 先增加新入口并让旧入口委托，再迁移调用点，最后删除旧入口。
- 禁止在一个提交中同时进行大规模目录移动和业务逻辑改写。
- 单个阶段发现需要改变业务逻辑时，立即停止该阶段并单独记录阻塞，不得自行扩大范围。

### 2.3 文件与编码原则

- 所有文件使用 UTF-8，推荐 UTF-8 no BOM。
- 新增 Python 模块必须在顶部说明功能和使用方法。
- 新增类、字段和函数必须具有能解释职责、参数、返回值和使用边界的注释或文档字符串。
- 目录移动必须使用 Git 可追踪的重命名方式，避免先删除再重新创建导致历史丢失。
- 每个阶段必须更新 `docs/change_history/YYYY-MM-DD.md` 和 `docs/change_history/README.md`。

## 3. 重构前基线

在开始任何移动前，必须建立并保存基线。基线结果作为之后所有阶段的对照组。

### 3.1 必须记录的基线

| 编号 | 基线 | 记录内容 | 通过条件 |
|---|---|---|---|
| BASE-01 | Git 状态 | 当前分支、commit、未提交文件列表 | 明确哪些改动属于用户，禁止覆盖 |
| BASE-02 | 后端测试 | `python -m pytest -q` 完整输出 | 记录通过、失败、跳过数量及既有失败 |
| BASE-03 | 前端单测 | `npm --prefix editor run test:unit -- --run` | 记录通过、失败数量及既有失败 |
| BASE-04 | 前端构建 | `npm --prefix editor run build` | 构建成功，或记录重构前既有失败 |
| BASE-05 | REST 契约 | FastAPI OpenAPI JSON 规范化快照 | 快照可重复生成且内容稳定 |
| BASE-06 | gRPC 契约 | protobuf descriptor 规范化快照 | service、RPC、message、field number 完整 |
| BASE-07 | 数据库 | 当前模型表、列、索引、外键快照 | 能和迁移后数据库逐项比较 |
| BASE-08 | Agent 流式协议 | 固定 fake model/tool 输入的事件快照 | 事件类型、顺序、字段稳定 |

基线产生的长期测试和契约快照应提交到 `tests/`；一次性日志、截图和命令输出放入当前任务的验收记录，不得散落在项目根目录。

### 3.2 既有失败处理

如果任一必需基线已有失败：

1. 记录失败测试、错误栈和复现命令。
2. 判断失败是否稳定可复现。
3. 本轮重构不得擅自修复无关既有失败。
4. 暂停依赖该基线的重构阶段，向用户报告阻塞；只有用户明确授权单独修复或明确排除该验收项后才能继续。
5. 最终验收不接受“相对既有失败没有恶化”作为通过；所有未通过项目必须列为未完成项。

### 3.3 验收资产和执行规范

阶段一必须创建固定的验收资产位置，后续阶段不得临时发明另一套输出目录：

每个自动化验收项必须在对应阶段记录中写明：

- 执行命令和工作目录。
- Python、Node、操作系统和关键依赖版本。
- 前置环境变量、模型、测试账号和 fixture。

## 7. 阶段三：统一数据库基础设施和迁移

对应 MW-BE-06。本阶段风险最高，必须单独实施，禁止与知识库或 Service 目录大搬迁合并。

### 7.1 实施内容

1. 新建 `core/db/engine.py`，提供唯一的 engine 和 session factory。
2. 将 Alembic 加入正式后端依赖，在项目中创建唯一的 `alembic.ini` 和 migration environment，建立能够从空数据库创建完整 schema 的基线 revision。
3. 将所有手写 `ALTER TABLE` 转换为带版本号的 migration。
4. `core/db/migration.py` 只封装 Alembic 的检查和升级入口，不自研第二套迁移系统。
5. 应用启动时，在任何 Service 访问数据库前统一执行一次升级。
6. 删除所有 Service 构造过程中的 `SQLModel.metadata.create_all()`。
7. 删除所有 Service 中的 `create_engine()` 和 schema 修改 SQL。
8. 所有数据库相关 Service 最终必须通过构造参数接收 session factory 或领域 repository；允许分多个提交迁移，但本阶段结束前迁移清单必须 100% 完成。

### 7.2 Alembic 基线、识别与备份策略

- **空数据库**：直接从 Alembic base 执行 `upgrade head`；基线 migration 必须创建完整 schema，禁止先调用 `create_all()` 再 stamp。
- **当前未版本化数据库**：迁移器先生成 schema fingerprint；只有与已登记的 legacy fingerprint 完全匹配时，才允许创建备份、stamp 对应基线 revision，然后继续 `upgrade head`。
- **历史数据库**：每一种已支持历史结构都必须具有脱敏 fixture、唯一 fingerprint 和明确起始 revision；禁止根据“缺哪列就补哪列”猜测版本。
- **未知或被手工修改的数据库**：拒绝自动迁移并阻止依赖数据库的 Service 启动，错误必须指出不匹配项和备份位置；禁止强行 stamp。
- **备份**：对非空 SQLite 数据库升级前，在同一受控 runtime 的 `backups/db-migrations/` 下创建带时间、源 revision 和 SHA-256 的一致性备份，并验证备份可打开后才开始 DDL。
- **SQLite 事务限制**：migration 必须假设部分 DDL 不可完全事务回滚；涉及表重建或数据转换时使用“新表—复制校验—切换”的方式，并在失败时恢复已验证备份。
- **降级**：可逆 migration 必须实现并测试 `downgrade()`；业务上不可逆的迁移必须明确标记，且只有在备份恢复演练通过后才允许上线。
- **命令入口**：开发和测试环境使用 Alembic 标准 `upgrade head`/`downgrade`；应用启动只调用 `core/db/migration.py` 中对同一 Alembic 配置的封装，不得存在两套 revision 状态。

必须在阶段记录中实际执行并保存以下命令的结果：

- `python -m alembic current`
- `python -m alembic history`
- `python -m alembic upgrade head`
- `python -m alembic downgrade <previous_revision>`，仅用于声明可逆的 migration 和数据库副本
- `python -m alembic upgrade head`，验证 downgrade 后可再次升级

### 7.3 数据迁移验收矩阵

| 场景 | 操作 | 通过标准 |
|---|---|---|
| 空数据库 | 从零执行 `upgrade head` | 所有表、列、索引和约束与目标模型一致 |
| 当前数据库副本 | 使用真实结构副本升级 | 升级成功，所有记录保留 |
| 各历史结构 | 从包含现有手写迁移前字段的 fixture 升级 | 每个历史 fixture 均可到达 head |
| 重复启动 | 连续启动两次 | 第二次不执行破坏性 schema 操作且不报错 |
| 中断恢复 | 在数据复制和表切换前分别注入失败，执行备份恢复后重试 | 数据库不处于不可识别的半迁移状态 |
| 新旧结果对比 | 比较关键表记录数和业务字段 | 记录数、主键和业务值完全一致 |
| 当前未版本库 | fingerprint、备份、stamp、upgrade | 只有登记结构可迁移，未知结构被拒绝 |
| 降级 | 对每个可逆 revision 执行 downgrade/upgrade 往返 | schema 和数据校验均通过 |

“关键表和业务字段”不得由实施者临时抽样。阶段一必须从全部 SQLModel 表生成 `database_manifest.json`，列出表名、主键、业务列、索引、外键、预期记录数校验方式和敏感字段脱敏规则；迁移验收覆盖该清单的 100%。

## 15. 提交、回滚与失败处理

### 15.1 提交粒度

- 每个阶段至少一个独立提交；大型阶段按“新增组件—迁移调用—删除旧入口—补文档”继续拆分。
- 纯移动和行为修改不得混入同一个难以审查的提交。
- 每个提交必须说明对应的 MW-BE 编号和已执行的验收项。

### 15.2 回滚条件

出现以下任一情况，立即停止继续拆分并回滚当前阶段，而不是在错误基础上继续堆兼容代码：

- 无法解释的契约快照变化。
- 旧数据库升级失败或数据差异。
- Agent 事件顺序、终止条件或工具调用行为变化。
- REST/gRPC 同一业务产生不一致结果。
- 新增循环依赖、第二套业务实现或新的全局 Service Locator。
- 实际界面冒烟出现数据损坏、无限加载或无法关闭的后台任务。

### 15.3 完成报告

最终报告必须逐项列出：

- 完成的 MW-BE 编号。
- 每项对应的代码路径。
- 自动化测试命令及结果。
- 契约快照对比结果。
- 数据库迁移测试结果。
- 实际界面冒烟结果。
- README 和 change history 更新位置。
- 未完成项、阻塞原因和对用户行为的影响。

任何未完成项都必须明确报告，不得以“基本完成”“MVP 完成”或“视觉近似”代替验收通过。
