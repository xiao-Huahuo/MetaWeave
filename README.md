## 简介


### 现实痛点

资料随机掉落在 Markdown、PDF、Office 文档、图片、表格和代码中。
纯粹的文件库擅长保存文件，却很难让 Agent 统一检索和操作这些不同结构的知识资产。

### 产品定位

**MetaWeave(元织)** 是一款**AI原生**的、以**多模态**为基础、以**多知识形态**为根本、以**Agent**能力全面智能集成的**本地个人知识库**. 
- **多模态支持**: Markdown、LaTeX、纯文本、CSV、TSV、代码、DOCX、XLSX、PPTX、PDF 和常见图片格式, 均可在桌面工作台中实时查看,并内置**全模态转Markdown**的能力.
- **多知识形态**: 文件库、图书馆、智能表格、组件库、密码库和文献库，六库均配备在**统一的大知识库**，由Agent统一调度，从根本上杜绝混乱的知识存储机制来源。文献库建立在智能表格之上：智能表格负责结构化整理和批量比较，文献库负责按篇浏览、阅读和编辑，两处数据始终对应同一份文献记录。


### 主要服务人群

- 希望在个人文件系统上建立 Agent 中枢的知识管理用户。
- 需要统一管理文档、文献、表格和代码等异构资料的用户。
- 希望自行配置模型、工具和工作流的开发者。

### 设计原则

Agent 框架不能消除模型幻觉。MetaWeave 因此优先提供检索、引用、执行轨迹和调试观测，让用户能够核对依据并发现问题,这也是`引用溯源`功能的设计来源。

## 技术与环境
### 环境要求

当前正式发行版支持 **Windows 10/11 64 位（x86-64）**，不支持 macOS、Linux 或 Windows ARM。

| 项目 | 支持范围 |
|---|---|
| 操作系统 | Windows 10/11 64 位 |
| 处理器 | x86-64 处理器；建议 4 核或以上 |
| 内存 | 基础功能至少 8 GB；使用本地 Qwen、Embedding、ReRank 或 OCR 时建议 16 GB 或以上 |
| 存储 | 安装与基础运行至少预留 2 GB；下载并使用全部本地模型时建议预留 10 GB 或以上 |
| 图形硬件 | 不要求独立显卡或 CUDA；当前正式发行版使用 CPU 推理 |

### 技术栈
* 版本：Python 3.12
* 微服务框架：FastAPI
* 通信与工具协议: gRPC + REST/HTTP + MCP
* 观测面板：Vue 3 + Pinia + TypeScript/JavaScript
* 知识图谱：D3.js + Canvas
* 文档编辑器：CodeEditor + MarkdownPreview + PDF/多模态原件预览器，按文件类型切换编辑、LaTeX 编译、图片、视频、表格或 Markdown 中间层预览
* 反向代理：Vite
* 智能体编排：LangGraph + LangChain
* 模型接入：以 `DeepSeek-flash`作为正式测试版, 同时支持用户配置的 OpenAI 兼容大小模型接口，并以内置 CPU 本地大模型`Qwen/Qwen3.5-2B` 提供未配置时的本地回退.
* coding agent子智能体: [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness.git)；
  * MW当前锁定上游提交 [`47f943859bef60e4160492346772ded9b24f765a`](https://github.com/deepseek-ai/deepseek-harness/commit/47f943859bef60e4160492346772ded9b24f765a)，叠加仓库内 MW补丁后生产 `0.1.0-rc.5+mw.1` Runtime SDK，并将成品随 MW仓库和 EXE固定发布。
* 关联数据库：SQLite
* 向量数据库：ChromaDB
* 记忆与语义检索方案：RAG（向量检索 + 关键词检索 + ReRank）
* 配置管理：Pydantic / dataclass 风格 AgentConfig
* 异步任务：asyncio
* 知识库文件监听: watchdog
* 联网搜索引擎: DuckDuckGo + ddgs
* OCR引擎: PaddleOCR
* 日志与监控：logging / structlog + Prometheus + Grafana
* 测试与质量：Pytest + Ruff + mypy
* 前端图标: dsh + Morphicons + Lucide

### .mw 知识库内锚点

每个知识库根目录下都有一个由 MetaWeave 管理的 `.mw/`。它是应用功能在该知识库内的固定锚点：多模态中间层、图书馆、智能表格、组件库和 LaTeX 编译缓存都从这里定位。文件树可以显示 `.mw/` 供用户查看受管文件，但其中内容不会作为普通源文件重复灌库，也不允许在存储设置中单独改到其他位置。

```text
<知识库>/                                  # 用户当前知识库根目录
├── 用户文件与目录                  # Markdown、PDF、Office、图片、代码等原始资料
└── .mw/                                   # MetaWeave 管理的知识库内固定锚点
    ├── md/                         # 按原目录映射的 Markdown 中间层
    ├── frontmatter/                # 结构化 JSON、资源引用与 source map
    ├── assets/                     # PDF、Office 等文档抽取出的图片
    ├── library/                    # 图书馆图书与集锦目录
    ├── forms/                      # 智能表格及其文献附件
    ├── components/                 # 组件库中的 Vue 与 HTML 文件
    ├── scan/                       # 扫描器原文件、Markdown 草稿与解析资产
    └── latex/                      # LaTeX PDF、AUX、LOG 与 SyncTeX 编译缓存
```

`md/`、`frontmatter/` 和 `assets/` 主要由原文件派生，必要时可以重新灌库生成；`library/`、`forms/`、`components/` 和 `scan/` 包含用户管理的业务内容，备份知识库时应与原始文件一起保留。切换活动知识库时，应用使用的 `.mw/` 也随之切换。

## 详细功能设计

以下是 MetaWeave(元织) 的核心功能,部分业务工作流流程图可见[WORKFLOW.md](docs/WORKFLOW.md).

### 六类知识库

#### 多模态文档库

多模态文档库是建立在文件系统上的, 集 "多模态转Markdown + Agent知识库记忆 + 知识图谱实体关系抽取" 为一体的,以 Obsidian 作为灵感来源,并进行**模态解析功能增强**和**Agent智能化集成**的高级文件系统.

##### 灌库管理

**系统可以解析 Markdown、LaTeX、纯文本、CSV、TSV、代码、DOCX、XLSX、PPTX、PDF 和常见图片格式，并将结果转换为Markdown格式,以及可供Agent检索的格式。**
"灌库"的含义是将多模态的文件转换为统一的 **Markdown 中间层**，并按需要保存 frontmatter、文档内图片和其他附件。
这些派生文件位于知识库的 `.mw/` 目录，由 MetaWeave 管理，编辑器预览、搜索、图谱和 Agent 检索共用这份解析结果。
- 文件树使用不同的索引状态图标区分已灌库、未灌库或格式不可识别、已屏蔽三类文件，分别显示为绿色、红色和灰色。
- 默认采用惰性灌库：文件进入知识库时不自动写入向量库，用户可以手动灌入单个文件，也可以通过顶部命令栏对整个知识库重新灌库。
- 用户可以屏蔽单个文件或建立屏蔽区。被屏蔽的文件不会灌库；已经灌库的文件被屏蔽后，系统会删除以该文件为来源的知识切片。灌库过程会自动忽略被屏蔽的文件及屏蔽目录的子树。
按照文件模态,灌库的方式如下:
- **Markdown** 和纯文本按标题、段落等结构处理；
- **JSON**、**JSONL**、**CSV**、**TSV** 和 **XML** 会保留可识别的结构信息;
- **HTML** 会忽略脚本与样式内容, 其他代码格式(如**PY**,**CPP**,则会根据语言进行选择性高亮。
- **DOCX** 会提取段落、表格和内嵌图片；
- **XLSX** 按工作表与表格内容处理；
- **PPTX** 从演示文稿结构中提取文字与媒体。旧版 DOC 和 PPT 不在专用解析范围内。
- **PDF** 会根据文本、扫描页和表格等内容选择解析方式。
- 常见图片(如**PNG**,**JPG**,**WEBP**,**GIF**)可以提取 OCR 文字、图片说明和基础元数据；
- 文档内嵌图片会保留所在段落、表格或页面附近的上下文。
- 没有专用解析器但可以解码的文件则按纯文本处理。
- 视频以及无法识别的二进制文件只登记资源信息，不进入灌库的语义索引。

图片、扫描型 PDF 以及文档内嵌图片可以使用 PP-StructureV3 提取版面、文字、表格、公式和阅读顺序。知识库 OCR 默认关闭，用户在设置页开启后会对后续灌库立即生效，无需重启应用。流水线按方向校正、版面分析、Server OCR、表格结构和公式识别的顺序串行工作，结构化 Markdown 进入 `.mw/md/`，版面块、坐标、页码和类型统计进入 `.mw/frontmatter/`。用户直接上传到 Agent 会话的图片会先完成同一套结构化 OCR，再交给 CPU 本地 Qwen 补充对象、空间关系和图表语义；两部分合并为附件正文。Agent 也可以调用“识图”工具，对当前会话中的指定图片提出新的视觉问题。

##### 编辑器与多模态查看
编辑器根据文件类型选择对应模式：

- **Markdown**：`Edit / Preview / Split`，支持源码编辑、渲染预览与分栏查看。分栏模式会同步编辑区与预览区的滚动位置。
- **纯文本**：`Text`，直接编辑原始文本。
- **代码与标记语言**：`Code`，提供语法高亮和编辑能力。
- **LaTeX**：`Code / Preview / Split`，编辑 `.tex` 源码、编译 PDF，或在同一工作区分屏查看源码与 PDF。
- **CSV**：`Text / Forms`，可以在原始 CSV 文本与表格之间切换。
- **XLS / XLSX**：`Forms`，以表格形式查看。
- **DOCX / PDF / 图片**：`Preview / Markdown`，分别查看原件和 `.mw/md/` 中间层全文。
- **PPTX**：`Preview / Markdown`，当前原件预览留空，Markdown 显示中间层全文。
- **视频**：`Preview`，MP4、WebM、Ogg/Ogv、MOV 与 M4V 使用内置播放器查看；视频默认屏蔽且始终不参与知识灌库。
- **其他格式**：可解码文本显示 `Text`；二进制文件显示 `Binary` 状态且不可查看。旧版 DOC 按不支持格式处理。

##### 对Obsidian风格的一些沿用

除常用 Markdown 语法外，MetaWeave 还支持 Obsidian 风格的 **Wiki 链接**、**嵌入链接**和**反向链接**查询。
- 原生 `<img>` 会显示为独立图片块，`<iframe>` 媒体嵌入会显示为自适应 16:9 视频块。
- 编辑 Markdown 时可以使用 `[[文档]]` 建立 Wiki 链接(也可以写成 `[[文档|别名]]` 或 `[[文档#标题]]`),点击即跳转到此文档相应的位置。
- 输入 `[[` 后会出现文档候选，继续输入文档名可以筛选；预览中的链接可以打开目标文档，带标题的链接会跳转到相应位置。
- `![[文档]]` 使用相同的目标与别名规则，但预览时直接嵌入目标内容，并在左侧显示主题色竖线。Markdown 之间相互嵌入时最多递归五层。
- 编辑器右键菜单提供“插入 Wiki 链接”和“插入嵌入链接”。
- 反向链接指向与 Wiki 链接相反的查询方向：打开某个 Markdown 文件后，可通过编辑区右键菜单的“显示反向链接”，编辑区底部会按来源文件列出所有链接当前文件的文档，并保留每一处链接在原文中的完整写法.

#### 图书馆

图书馆是知识库里的资料书架，把文件、文本和网页进行封面包装,**一一对应**成更适合阅读的"**虚拟卡片**".
从某种意义上,图书馆是另一种文件系统,建立在原本的混乱无章的库体系上,经过封面图片的映射,成为像"[小红书](https://www.xiaohongshu.com/explore)"一样的"**相册式存储系统**".

图书馆里有两类内容:**图书**和**集锦**:
- 图书是一份具体资料,可以来自文件、直接输入的文本或网页地址.
- 集锦是一组资料(图书的文件夹),适合整理论文、项目文档、课程材料、素材收藏等主题。

图书馆会维护真实文件位置。新增集锦会创建同名文件夹,新增图书会保存到当前集锦文件夹中。移动或重命名图书、集锦时,真实文件也会跟着移动。

- 真实文件固定保存在当前知识库的 `.mw/library/` 中；该目录由 MetaWeave 管理，在存储设置中只读展示。

- 标题会自动转换成可用文件名。系统会清理非法字符,遇到重名会自动追加序号,避免覆盖已有资料。

- 图书馆卡片会显示资料名称、描述、修改时间、灌库状态和图谱状态。用户可以按类型、标签和排序方式筛选。

如果真实文件被手动移动或删除,图书馆不会直接删掉卡片,而是标记为缺失。用户可以据此判断资料是否需要找回、重新加入或修正存储路径。

#### 智能表格
智能表格:面向**科研文献**的智能化字段管理表格.
智能表格适合整理和比较一批科研文献。每一行对应一篇文献，每一列记录一类信息，例如标题、作者、研究方法或阅读进度。新建表格时选择默认的“智能表格”，其中的文献会同时出现在文献库；在表格或文献库修改标题、标签、星级、智能字段与原文，两处会同步更新。
注: 智能表格也是文献库的数据来源。每一行智能表格对应文献库中的一篇文献，所属表格则作为文献分组；在任一页面修改标题、标签、星级、智能字段或原文，另一处都会同步更新。普通表格不进入文献库。

##### 从文献开始整理

1. 点击“新建表格”，填写名称并选择“智能表格”。新表默认包含序号、文献上传、标题、文献内容和图表等常用列。
2. 点击“上传文献”，为每一行添加一个文件。智能表格支持知识库能够解析的文档格式，上传后会自动灌库，提取正文与 PDF 图表，并根据正文生成标题等智能字段。
3. 按研究需要添加字段。内置字段包括公式、文献类型、重要性、阅读进度、关键词、摘要、期刊、作者、年份、研究背景、研究内容、研究方法、研究结果、创新点、局限性、未来展望、DOI 和 URL。
4. 检查自动生成的内容。智能文本和智能标签都可以直接修改，也可以重新生成单个单元格，或使用“全表智能填充”批量处理。生成失败或返回空内容时，表格会保留原值，避免覆盖已经整理好的结果。
##### 列字段分类
智能表格支持各种列字段,包括非智能字段以及智能填充字段:
  - 文本: 普通文本,可编辑.
  - 智能填充文本: 拥有文本的功能,并且自动将上传的文件内容和用户自定义的这个列标题通过LLM自动的异步生成文本,用户可编辑,编辑后可以点击格子右上角的图标按钮进行重新LLM生成,也可以直接保存.
  - 标签: 用户可编辑和增加和删除标签.
  - 智能标签: 拥有标签的功能,并且智能填充,具体生成过程是将现有所有此列的标签和提取的文字一起喂给LLM,LLM选择已有的(多个)标签或者自己生成新的标签.用户可编辑和增加和删除标签.
  - 选择框: 只能选择"是"或者"否",可编辑.
  - 星级: 只能选择1-5颗星,可编辑.
  - 日期: 可以调用待办侧边栏中的日历选择器输入日期和精确时间.
创建智能表格时带有默认列,如下:
  - 序号(文本): 从1开始自动生成,不可编辑.
  - 文献上传(特殊列): 拖拽上传任何知识库支持的格式的文件,自动灌库并提取文字备用.一列只能上传一个文件.
  - 文献内容(只读文本,其他所有智能列的内容来源): 用户上传文件之后显示抽取的文字内容,不可编辑.
  - 图表(只读Markdown预览): 汇总显示PDF灌库过程中抽取出的图表图片链接,新建智能表格默认包含.
  - 标题(智能填充文本): 提取文字后,自动智能填充,可编辑.
除了默认列之外,用户还可选择性的插入这些列:
  - 公式(智能填充文本): 从文献内容中提取主要LaTeX数学公式,过滤单个符号和过短表达式,并以`$$...$$`包裹后预览;新建表格默认不包含.
  - 文献类型(智能标签): 智能自动填充的标签列,用户可编辑和增加和删除标签.
  - 重要性(星级): 以星级形式显示,默认是空的5颗星,用户可以随时打星.
  - 阅读进度(标签): 只能选择"未读","已读","阅读中"三种标签,默认是"未读",用户可修改.
  - 关键词|摘要|期刊|作者|年份|研究背景(why)|研究内容(what)|研究方法(how)|研究结果|创新点|局限性|未来展望|DOI|URL (智能填充文本): LLM会异步的自动从上传的文献中提取这些信息并填充到表格中,不同的列用不同的彩色浅背景区分.所有内置列都带有简短的默认辅助描述,用于说明字段语义并指导LLM生成.

除此之外,用户还可以创建自定义列: 用户可以自定义列名和列的类型(仅提供内置类型),并插入到任何地方.

每一列都可以补充**辅助描述**:点击列图标即可编辑辅助描述,辅助描述将在每次智能填充时同步喂给LLM.

##### 表格规格调整

行和列都可以拖动排序，也可以调整宽度与高度。除内置字段外，还可以在任意位置添加自定义列，并选择文本、智能文本、标签、智能标签、是或否、星级、日期等类型。删除“文献上传”和“文献内容”两列后，表格会转为普通表格，不再使用文献解析与智能字段功能，也不会出现在文献库中。

顶部搜索框会匹配整张表格的内容，标签筛选和星级筛选可进一步缩小范围。需要清理批量生成留下的空字段或失败字段时，可以使用“清空无效字段”。

##### 文献预览与分屏阅读

文献上传列会显示图片缩略图或 PDF 首页预览。

点击文献可以在编辑器侧边栏查看原件；双击文献则会进入文献库中的对应阅读页面。若在侧边栏保存了修改后的原文，系统会重新灌库，刷新文献内容，并重新生成这一行的智能字段。

##### 导入与导出
表格可以导出为 Markdown、CSV 或 ZIP。Markdown 和 CSV 不包含文献上传列；ZIP 中包含 Markdown、CSV 以及用于保留表格结构的 `form.json`。

#### 文献库

文献库是智能表格的阅读视图, 由智能表格中偏向“横向比较”的一行一列转换形式, 成为适合“逐篇阅读”的文献列表与编辑区.
注: 文献库与智能表格文献来源完全共享,每一文献与智能表格的行一一对应.文献仍归属于原来的智能表格，也继续使用原表格的字段和原始文件。

一个知识库可以有多张智能表格，每张表格包含多行内容,每个文献块对应智能表格中的一行，并显示封面或文件图标、标题、真实文件名、文献内容摘要和入表时间。用户可以选择某张表格筛选表中的文献，也可以选择“All”浏览当前知识库中的全部文献。
- 标题、标签、星级、普通文本和智能字段都可以直接修改，修改结果会同步回智能表格；新增字段、智能填充、重新上传和清空无效字段也沿用智能表格的能力。
- 点击文献可以在同一页面的编辑区查看原文；从智能表格双击文献上传单元格，也可以直接进入该文献对应的文献阅读页面。这样既保留表格的批量整理效率，也避免文献阅读退化为普通文件树。
- 文献库支持按标题、文件名和内容搜索，并可按标签、星级、表格、标题、文献大小、入表时间或最近浏览时间筛选和排序，便于在多张表格之间持续阅读和定位资料。

#### 组件库

组件库用于集中收藏、浏览和复用带有真实交互与动效的界面组件。

组件按 all、buttons、checkboxes、toggle switches、cards、loaders、inputs、radio buttons、forms、patterns、tooltips 和“绘图脚本”分类筛选，以自适应尺寸的"瀑布流"卡片展示，小型组件不会被强行撑大，较高或较宽的组件也会按照自身内容自然排布。

- 支持 Vue 单文件组件和独立 HTML。组件会在隔离的实时预览区中编译并显示，按钮、开关、悬停动画等交互可以直接在卡片或详情页中体验。
- 点击组件内容会触发组件自身的交互；点击详情按钮则会进入更大的实时预览与源码对照页面。详情页支持一键复制源码，并允许直接在原位置重命名组件。组件卡片上的名称同样可以直接修改，不需要打开额外表单。
- 上传组件时可以填写组件名、粘贴源码并立即查看编译结果，再为组件选择一个分类标签。也可以从文件资源管理器一次选择一个或多个 Vue、HTML 文件批量加入组件库。
- 单个组件源码最多可保存 2,000,000 个 Unicode 字符，可容纳超过 1 MiB、超过 100 万字符的源码。超过 100 万字符时仍会完整保存、编辑和复制，但不会自动生成实时预览，以避免浏览器主线程因编译超大源码而失去响应。
- “绘图脚本”使用独立上传模式：源码原样保存而不编译，脚本语言既可输入自定义值，也可从内置选项中选择。可选上传图片封面；未上传时卡片以组件名作为文字封面，并在类型标签旁显示脚本语言。
- 组件统一保存在当前知识库的 `.mw/components/` 中。

#### 密码库

密码库模仿[BitWarden](https://bitwarden.com/)建立,用于集中保存账号、支付卡、身份资料和安全笔记。

密码库有独立的主密码，进入密码库时需要单独解锁；手动锁定或解锁状态过期后，只需再次输入主密码，不会退出 MetaWeave。

##### 开始使用

首次进入时，先创建并确认主密码，主密码至少需要 8 位。以后打开密码库时，输入这组密码即可解锁。完成查看或编辑后，可以点击右上角的“锁定”，立即结束本次密码库会话。

点击“新建”并选择条目类型，然后填写对应内容：

- 登录条目需要项目名称和密码，还可以记录用户名与网站地址。
- 支付卡需要项目名称和卡号，可补充持卡人、品牌及安全码。
- 身份资料需要项目名称和名字，可继续填写公司、电子邮箱、电话与地址。
- 安全笔记需要项目名称和笔记内容，适合保存不属于前三类的私密文字。

每类条目都可以添加图片、标签和备注。保存后，可以继续查看或修改；密码字段支持临时显示与隐藏。

##### 查找与管理

侧边栏可以搜索密码库，并按条目类型或标签筛选。删除的条目会先进入回收站，可以恢复，也可以永久删除；永久删除后，条目关联的图片也会一并清理。

如需更换主密码，可以前往“设置 → 安全”重置。系统会使用新密码重新加密已有条目，并使之前的密码库会话失效，之后需要使用新密码解锁。

##### 导入与导出

密码库支持导入 JSON 文件，也可以导出整个密码库或选中的条目。无法匹配现有字段的可识别内容会转为安全笔记，导入结束后页面会显示成功、转换和失败的数量。

导出的 JSON 包含密码、安全码和安全笔记等明文内容。导出前请确认保存位置可信，使用后及时转移或删除文件，避免被其他程序或用户读取。

> **安全限制：** 当前版本会在本地数据库中保存一份供调试功能读取的主密码副本，“设置 → 安全”页面还提供无需旧密码的重设入口。在移除这些调试能力之前，请勿用密码库保存真实账号密码、支付卡信息或其他高敏感资料。

### Agent能力

#### 模型说明
##### 模型选型
项目提供一个`Qwen3.5-2B`多模态模型作为轻量级本地大模型,用户可在"设置-存储管理-模型管理"中手动下载和加载.该模型不依赖GPU和CUDA,可以在中低端设备上兼容.

注: **建议采用`deepseek-flash`作为大模型和小模型API**;不建议使用本地模型作为主要模型,因为其输出很慢,不好用.
##### 大模型API设置
用户可在 "设置-LLM配置" 中输入联网大模型的模型名称和URL和API-Key.

- 未配置大模型的相关内容时,默认采用本地大模型作为大模型回答; 
- 若用户设置了大模型API,则自动使用用户设置的作为大模型和小模型的回答来源(未配置小模型API时则用大模型API作为回退).

##### DeepSeek思考与流式输出

DeepSeek 接入使用专用适配器保留 `reasoning_content`,并在带工具的后续请求中按 DeepSeek协议回传本轮思考内容。模型流中的 reasoning、正文 content和 tool calls是三个彼此独立的通道:同一个chunk即使同时包含思考、正文和工具调用,也会分别处理,不会因为进入思考或工具阶段而吞掉正文。

本地调度器和 Redis调度器使用相同的 reasoning/content事件语义。每次模型调用结束时只记录原始正文、已流正文、终态正文和终态补齐的字符数,以及正文chunk数量、最大正文chunk字符数、混合字段chunk数量等不含正文的`stream_diagnostics`;正常连续输出时终态补齐字符数应为0。前端仍保留终态全文校正作为数据完整性兜底,并单独记录实际校正字符数,用于定位provider、代理或客户端发生的丢流,而不是用表现层隐藏问题。

#### 智能体状态转移设计
在LangGraph状态转移图入口处有一个入口节点,调用一次小模型,按照用户提问内容区分三种模式的入口,用户在同一session前后提出简单和困难的问题时,会以小模型决策以下三种图的模式:
      1. 简答模式: 对于明显不需要思考的短输入,不经过循环,只保留 RAG 上下文构建,用小模型直接输出.
      2. ReAct模式: 不经过`planner`节点和`observation`节点,标准的ReAct图.agent节点同时充当观察者和决策者,一个循环只需要调用一次LLM.
      3. 深度思考模式(Plan-and-Execute模式): 经过规划-执行-观察的循环,一个循环会调用2~3次LLM,适合长时间思考.
   auto模式会先调用小模型路由器输出`simple/react/plan`,显式选择模式时不经过路由器;当小模型认为自己能力不足、不确定能否可靠回答、需要事实核验或外部信息时,至少进入`react`,不能选择`simple`;当小模型不可用或输出无法解析时,才回退到本地保守规则.
   前端提供 `auto`/`simple`/`react`/`plan` 思考模式切换,Agent 观测面板状态图按实际执行模式切换.
##### 节点设计
节点有以下几种：
   * 启动/终止节点 `START`/`END`
   * 决策/汇合节点 `agent`
   * 工具调用节点 `action`
     * 跨会话记忆检索
     * 上下文压缩与事实持久化
     * 知识库检索
     * 其他内置工具
     * MCP外部工具
   * 安全审核节点（输入/输出两阶段）,包括:
     * 输入安全审核（入口）`safety_input`
     * 输出安全审核（出口）`safety_output`
   * 推理规划节点 `planner` : 具备全局规划思想,拆解问题, 跨轮保持计划 + sub_question 状态机 + 绕圈检测,成为agent执行节点的"调度者".
   * 反思节点 `observation`: 根据观察选择路径,可选性的规划而不是每次都进入planner节点. 产出四种状态.
      首次: planner（拆解问题，出 sub_questions）
      agent → action → observation（精炼结果 + 提取事实 + 判方向）
      │ 针对observation的不同输出
      ├─ [continue] → planner（更新计划）→ agent（继续）
      ├─ [answer]   → agent（出最终回复）
      ├─ [retry]    → agent（换参数重试同一工具）
      └─ [abandon]  → agent（承认查不到，给出已有信息）
   * 摘要节点 `summary`
   * 上下文压缩节点 `compress`

#### 多Agent能力
Agent可以召唤子Agent,采用"**Agent蜂群**"(父子Agent)设计模式.子Agent由主Agent启动,并接收包含角色、目标、可用工具、权限边界和交付格式的"子任务合同".子Agent完成后,结果进入按父Agent隔离的内存队列.生命周期如下:

```
created → running → completed
         ↘ failed
         ↘ stopped
```

主Agent可选择的真实子Agent类型为 `explore`、`dsh`、`coding`:

- `explore`用于只读调查;
- `dsh`使用内置 DeepSeek Harness Runtime完成代码任务;
- `coding`是DSH未启用时的MW原生代码后备.

子Agent在线程池中独立运行,拥有独立上下文.沙盒权限不能高于父Agent;Native子Agent的工具取父Agent授权范围与父Agent自身能力的交集,DSH子Agent则使用与权限模式对应的固定 `dsh.read/search/edit/pwsh/git/test` 能力.**主Agent不能授予自己没有的能力**,子Agent也不能继续召唤其他子Agent.

- 子Agent分为前台和后台两种模式:
  - 前台子Agent(同步阻塞):主Agent等待该子Agent完成后再继续,适合有前后依赖的任务.
  - 后台子Agent(异步蜂群):不阻塞主Agent,可以并行启动多个子Agent;主Agent可继续处理其他工作,随后显式等待结果,也可请求停止仍在运行的子Agent.
- 角色与身份: `agent_type`是模型必须显式选择的真实运行类型;旧的category/provider只作为内部兼容字段,不再暴露给模型。主Agent可以为子Agent起名,不命名时按类型自动生成递增名;每个子Agent按运行ID稳定分配一个头像,整个会话期间保持不变,方便持续追踪同一任务。
- 后台显式汇合:主Agent召唤后台子Agent后,反复调用"等待子Agent"工具逐个收取结果。该工具每次最多返回一个终态结果;可以限定run ID,不指定时则等待当前范围内任意一个子Agent。结果已入队时立即返回,否则阻塞到下一个结果或超时。只要目标范围内仍有子Agent处于 `created` 或 `running`,主Agent就继续等待,全部进入终态后再汇总最终回答。
- 可见性:创建、开始、完成、失败和停止等生命周期事件实时进入主Agent对话流,并渲染为可展开的事件条。子Agent侧边栏每2秒刷新一次状态,按目标合并任务卡片,展示头像、名字、类别、前后台模式和状态;完整的Native子Agent对话可在独立抽屉查看,DSH执行过程可通过只读Web查看。后台子Agent在主Agent流结束后才完成时,系统会补充一条完成事件;已经在流内推送的终态事件不会重复提醒。
- 运行控制:主Agent可请求停止子Agent,子Agent会在协作式安全检查点响应。管理层还保留上下文更新消息接口,但当前Native和DSH正式执行器尚未消费这些更新,因此运行中上下文注入不作为现有可用能力。

##### DSH 特殊子Agent

“基础设置 → 启用DSH”默认关闭。启用后,代码修改、命令、Git、测试和构建任务统一使用`agent_type=dsh`;关闭时使用`agent_type=coding`作为Native后备。`dsh`和`coding`都必须提供工作区绝对路径,且权限不能高于父Agent。

DSH子Agent复用同一个稳定的 Harness Session,支持主Agent使用`continue_child_agent`继续追问,不会把每次追问拆成互不相关的新会话。运行时由应用生命周期管理,首次使用时从EXE内置ZIP校验并懒解压;对话区展示生命周期、摘要和结果,需要查看完整过程时打开同一Runtime提供的loopback只读Web。只读Web拒绝写操作,进程由Windows Job Object托管并随应用退出回收。

#### 可观测性与可定制性
##### 对话内观测
Agent对话框分为"对话模式"和"工具模式":
  - 对话模式:合并连续的Assistant消息,模型reasoning和运行轨迹默认折叠,最终回答以完整对话气泡呈现.
  - 工具模式:按Agent节点和工具调用保留独立消息条,显式展示reasoning、工具参数、执行状态和结果.
  - 模型reasoning与`simple/react/plan`运行模式是两个概念:前者是单次模型调用返回的思考通道,后者决定LangGraph采用的执行图.
##### 观测面板(Debug)
Debug 页面用于直接检查 Agent 和后端运行时的真实数据。页面会加载当前 Session 的历史消息，并在“Agent 轨迹”“多模态灌库”“记忆与知识”“工具注册表”“API”五个页签之间切换。

- **Agent 轨迹**：左侧按当前运行模式展示本轮 Agent 的reasoning、节点轨迹和工具调用过程；右侧按调用顺序保存并切换每一次实际提交给模型的请求快照。快照包含最终messages、完整工具schema、主/小模型层级、模型名、温度、超时、扩展参数和动态上下文预算,但不包含API Key;可以在可读格式与Raw数据之间切换。终态消息元数据另行保存`stream_diagnostics`,可通过原始消息或事件接口核对已流正文与最终正文是否一致。
- **多模态灌库**：提供一套独立的知识库文件浏览器，可以前进、后退、返回上级、排序并查看文件灌库状态。双击文件后，右侧会生成该文件的 Markdown 中间层、JSON 结构化结果、语义章节和带重叠窗口的最终切片，同时显示章节数、切片数和窗口/重叠参数。该过程只用于观测，不会向向量库写入记录；已有且未过期的结构化结果会直接复用。
- **记忆与知识**：分别展示当前 Session 的知识库召回和长期记忆召回，可以对比 ReRank 前后的候选条目，并查看向量分数、关键词分数、召回通道、匹配词、ReRank 分数和最终分数。页面同时提供长期规则与长期记忆的手动添加、查看和删除。
- **工具注册表**：读取 Agent 当前实际注册的工具，按分类显示工具数量、参数数量和启用状态。用户可以搜索工具、查看说明与完整参数 Schema，也可以直接启用或关闭某个工具；开关结果保存到当前用户的工具设置。
- **API**：从正在运行的后端读取 REST 路由和 gRPC 方法。列表显示接口名称、方法、路径、请求、响应和运行状态；展开后可以查看 REST 参数、请求体、状态码与 Schema，或查看 gRPC 调用目标、流式类型以及输入输出消息结构。

##### 可定制性
* 用户自定义长期记忆:用户可以管理长期记忆,可以增加新的自定义长期记忆注入到向量库,或者删除长期记忆.
* 用户自定义系统提示词:用户可编辑"用户设置系统提示词",追加到原本的系统提示词中.



#### 引用溯源

引用溯源用于说明回答中的事实来自哪里。系统只展示最终回答实际使用的来源，不会把所有搜索命中结果都堆在消息下方。

回答中的引用编号有四种形式：

- `[1]`、`[2]`：本轮对话自动召回的长期记忆或知识片段。
- `[K1]`、`[K2]`：Agent 主动读取或通过四库联合搜索采用的来源，可以挂载文件库、图书馆、组件库和文献库中的原生结果。
- `[N1]`、`[N2]`：联网搜索使用的网页来源。
- `[A1]`、`[A2]`：用户在当前会话中上传的文件。

引用通常写在具体事实、判断或段落的末尾。例如，回答某个知识库文件中的内容时，会在对应句子后标注 `[K1]`；引用网页中的最新信息时，会标注 `[N1]`。引用编号只对应本轮实际可用的来源，系统不会接受模型自行编造的编号。

来源的展示遵循“实际使用优先”原则：

- 搜索结果只是候选来源，只有真正支持最终回答的内容才会出现在消息下方。
- 明确读取的本地文件可以作为回答依据；只被搜索到但没有被采用的文件不会自动列出。
- 网页来源必须在使用相关事实的位置明确标注，未被回答引用的网页不会出现在来源列表中。
- 如果回答遗漏了本地文件引用，系统只会在能够根据文件名或标题准确匹配回答内容时补充；无法确认时不会强行添加来源。

正文中的引用编号和消息下方的来源列表可以点击。点击带四库结果的 `[K#]` 会像点击回答下方挂载的原生结果块一样，在右侧展开对应库类型的侧边栏：文件库来源进入右侧编辑区，图书馆、组件库和文献库来源进入各自的原生结果侧栏。其他本地引用会打开或预览对应文件，网页引用会使用默认浏览器打开网页。每条历史消息保存自己的来源信息，因此重新查看历史对话时，引用仍然对应当时使用的文件和网页，不会被后续对话覆盖。

#### 安全设施
##### 安全审核
采用**三层递进式**安全防线,在 Agent 输入和输出两个位置执行审核,阻断风险请求并清洗敏感输出。
* 输入审核范围：`safety_input`只审核用户真实问题本身。当前端或`ContextBuilder`把“引用文档片段 + 用户问题”组合成一条`HumanMessage`时,安全审核会先抽取`用户问题:`之后的真实 prompt,不会把引用材料正文当作用户意图来拦截。这样总结、阅读、分析知识库文件时,文档正文中的敏感词不会误伤正常文件问答;如果用户问题本身命中风险规则,仍然会正常拦截。
* 第一层 — **敏感词初检**：
    在请求进入 Agent 主循环前,使用分类词库（`resources/safety/sensitive_words.json`）执行快速的"精确匹配 + 正则匹配"。
   词库按 `政治危险/色情/暴力/非法/垃圾广告/提示词注入/数据窃取` 七大类分组,
   每类标记风险等级（high/medium/low）, high 级别命中直接拦截,medium 级别交由第二层进一步判断。
* 第二层 — **小模型意图审核**：
   敏感词初检通过后,使用小模型对用户意图做语义级安全判断, 审核维度包括：恶意攻击（越狱/注入）、非法请求、信息窃取、骚扰滥用、正常请求。输出 `pass / block / suspect` 三态裁决。
* 第三层 — **输出审核**：
   在 Agent 生成最终回复后、返回用户前,对输出内容执行敏感词扫描。命中拦截类敏感词（政治/色情/暴力/违法）直接替换为标准安全回复;
   命中清洗类敏感词（广告/Prompt注入/数据窃取）执行脱敏替换（`***`）。
* 拦截回复差异化生成：
   被拦截的用户请求根据拦截类型调用**小模型**生成两类差异化回复：
       * 政治敏感：命中"政治危险"分类或意图审核判定"政治敏感" → 小模型生成"立场正确的反驳性回复"（如"这种说法是完全错误的。中国共产党始终坚持……"）。(先有意识形态,再有意识这一块)
       * 一般拦截：色情/暴力/违法/注入/广告等其他类别 → 小模型生成脱敏的礼貌拒绝（如"对不起,我不能回答这个问题,因为`[脱敏理由]`。如需其他帮助请随时告诉我。"）。
   两项回复均有对应的内置系统提示词,经小模型生成最终回答;小模型不可用时回退到静态后备文案。
用户可自行设置是否开启敏感词初检,或者自行设置是否开启安全审核总开关.
##### 终端沙盒

Agent 通过内置工具 `run_terminal_command` 获得非交互式终端能力。该工具不接受整条 shell 字符串,必须传入结构化参数: `shell`、`cwd`、`segments`。`segments` 分为两类:

- `internal_command`: 由后端直接实现,不经过系统 shell。读取类包括 `pwd`、`ls/dir`（支持 `-R`/`/s` 递归和 `*.docx` glob 通配符）、`cat/type`、`head`、`tail`、`stat`、`wc`（支持 `-l`/`-w`/`-c` 标志和多文件）;写入类包括 `write`、`append`、`touch`、`mkdir`（自动 `-p`）、`rm/del`、`mv/move`。所有内部命令已移除单文件/单路径限制,支持多参数批量操作。
- `external_program`: 通过 `subprocess.run(..., shell=False)` 执行。受权限模式控制:沙盒模式下走白名单+安全参数校验;完全访问模式下跳过白名单,仅拦截嵌套 shell（`cmd`/`powershell`/`bash`/`sh`/`wt`）和 `python -c`、`node -e`、包安装、`git push` 等高风险入口。

终端权限和文件工具权限分开控制:终端权限调控内部读写指令、外部程序和路径边界;文件工具只操作当前知识库,只读模式会拒绝写文件、删除、重命名、建目录、保存附件和重建知识库等写操作。

| 权限 | 终端读 | 终端写 | 终端外部程序 | 文件工具读 | 文件工具写 |
|---|---|---|---|---|---|
| 只读 | 全目录可读 | 禁止 | 禁止 | 知识库内可读 | 禁止 |
| 沙盒 | 全目录可读 | 仅终端工作区内 | 仅终端工作区内，且白名单/安全参数 | 知识库内可读 | 知识库内可写 |
| 完全访问 | 全目录可读 | 全目录可写 | 全目录可用，跳过白名单，仅拦截嵌套 shell 等高风险入口 | 知识库内可读 | 知识库内可写 |

#### 多级队列与限流
**模型任务调度器**统一管理所有 LLM 调用。内部多级队列按主 Agent、Summary、Fact Extraction 三个等级分配,同时设置 `large / small` 双模型池路由——主推理走大模型池,摘要/事实抽取/上下文压缩走小模型池,分别配备独立并发上限、超时、熔断与重试机制。
    * 大小模型分流机制：调度器按任务类别决定使用大模型还是小模型。
      * 主回答模型负责复杂推理与最终高质量回答.
      * 小模型负责重要事实摘要、长期记忆摘要、事实抽取、分类与轻量语义压缩,以降低主模型的延迟与负载压力。
    * 物理模型隔离：
      * 用户没有配置可用大模型时，`Qwen/Qwen3.5-2B` 通过现有 CPU PyTorch 同时承担主模型和小模型任务；孤立的小模型配置不覆盖这一回退;
      * 用户配置了大模型但没有配置小模型时，小模型任务复用大模型的模型名、Base URL 和 API Key，但仍占用小模型池的并发配额;
      * 大小模型都配置时分别调用各自配置，内置 Qwen 仍供直接上传图片的视觉理解与“识图”工具复用.

#### 上下文
* 不超过上下文长度的直接追加到上下文，超过最大上下文阈值时会先进入 `compress` 节点,用小模型生成“重要事实摘要”,再把工作上下文重写为 `重要事实摘要 + 最近少量消息`。
* 上下文拼装优先级为 `短期历史消息 -> 压缩摘要 -> 历史摘要/事实 -> 外部知识库片段`，避免知识库内容覆盖用户刚刚明确给出的事实。

##### 动态上下文拼装

动态上下文拼装在**每次真实模型调用前**，依据当前模型的实际 token 容量决定本次请求放入哪些系统规则、工具定义、历史消息、工具结果、压缩摘要、Skill、附件与检索内容。它只生成本次请求的预算内表示，不修改或删除数据库中的完整消息和工具结果；当前实现已移除 900、240、200、6000 等彼此无关的模型可见字符裁剪。

- **有效窗口**：100 万 token 只作为服务 ceiling；主模型和小模型分别使用自身的真实窗口。未指定请求级收紧值时，令 $C_{\mathrm{request}}=+\infty$：

$$
W_{\mathrm{eff}}=\min\left(C_{\mathrm{service}},\ C_{\mathrm{model}},\ C_{\mathrm{request}}\right)
$$

未填写模型窗口时直接令 $C_{\mathrm{model}}=C_{\mathrm{service}}=1{,}000{,}000$，不再回退到 128K；设置页主模型和小模型的上下文窗口默认值也统一为 `1000000`。

- **输入预算**：从有效窗口中扣除输出预留 $O$ 和 tokenizer/协议安全边际 $S$。$M_{\mathrm{out}}$ 是模型最大输出，$r_{\mathrm{out}}$、$r_{\mathrm{safe}}$ 由全局 Config 集中管理：

$$
O_{\mathrm{target}}=
\begin{cases}
O_{\mathrm{request}}, & \text{显式指定输出预算},\\
\left\lceil r_{\mathrm{out}}W_{\mathrm{eff}}\right\rceil, & \text{未显式指定},
\end{cases}
\qquad
O=\min\left(M_{\mathrm{out}},\ O_{\mathrm{target}}\right)
$$

$$
S=\left\lceil r_{\mathrm{safe}}W_{\mathrm{eff}}\right\rceil,
\qquad
B_{\mathrm{input}}=W_{\mathrm{eff}}-O-S
$$

- **固定成本与弹性池**：设 $T(\cdot)$ 为使用当前模型 tokenizer 对最终序列化内容的计量，固定成本 $F$ 先完整扣除，剩余预算 $P$ 由历史、工具结果、压缩状态、记忆、附件和检索内容共享：

$$
F=T(\mathrm{system})+T(\mathrm{current\ user})+T(\mathrm{protocol})+T(\mathrm{tool\ schemas})+T(\mathrm{mandatory\ skill})+T(\mathrm{safety})
$$

$$
P=\max\left(B_{\mathrm{input}}-F,\ 0\right)
$$

拼装过程如下：

1. 根据本次实际使用的主模型或小模型解析 `W_eff`、最大输出和 tokenizer，生成统一预算对象。
2. 序列化系统规则、当前用户请求、工具 Schema、强制 Skill 等固定块，计算 `F` 和弹性池 `P`。
3. 将普通对话轮次、`assistant tool_call + 对应 ToolMessage`、压缩摘要、记忆、附件和检索片段转换为不可破坏工具配对的候选原子组。
4. 按“当前请求与规则 → 当前未完成工具 cycle → 计划与未完成动作 → 近期相关历史 → 相关记忆/附件/检索 → 已完成旧历史”的优先级装入 `P`。
5. 候选组放不下时依次选择 `完整原文(full) → 结构化结论(structured) → 头尾与省略说明(head-tail) → 摘要、内容引用和继续读取方法(reference)`；禁止只留前缀或静默丢尾。
6. 某个大候选仍放不下时继续检查其他候选，不得像旧滑动窗口一样直接停止并丢掉它之前的全部历史。
7. 对最终序列化消息和工具 Schema 重新计量；若仍超过 `B_input`，从最低优先级内容开始逐级降级，校验工具调用配对后生成与真实提交一致的 Debug 快照并调用模型。

动态拼装与下方的上下文压缩相辅相成：**动态拼装管理当前这一次模型请求，压缩机制整理跨轮累积的长期历史**。达到压缩阈值后，小模型把旧历史重组为重要事实、历史动作和未完成动作；下一次动态拼装再把“压缩状态 + 最近消息 + 当前工具结果”按同一预算重新组装。压缩器不再裁剪工具结果，工具、Planner 和 Observation 也不得绕过动态拼装器私自设置模型可见字符上限。

##### 上下文压缩机制

上下文压缩采用“**大窗口滑动上下文 + 阈值摘要压缩 + 结构化状态独立保留**”的并行机制,并辅以长期记忆,使得Agent在压缩上下文的时候还能记住部分高质量的用户会话历史和事实。
三种机制职责不同：滑动窗口限制本轮工作集，摘要保存被移出窗口的信息，结构化状态保证任务与执行过程不丢失.

- **真实计量**：上下文长度由后端对本轮实际序列化消息进行模型感知的 token 统计。前端只展示后端返回的“当前工作上下文 token / 可用上下文上限”，不统计完整聊天记录，也不自行用字符数估算；工作上下文改变后，后端立即推送最新统计。模型上下文上限减去系统提示、工具定义、当前用户输入、附件/RAG 内容和预留输出 token，任何滑动或压缩都不得删除原始会话记录。
- **分级触发**：滑动窗口持续控制工作集；当实际占用达到模型窗口的一定比例时，再同步进入摘要压缩。触发阈值和压缩目标按模型窗口比例计算, 压缩后降到明显低于触发线的安全区间，避免连续多轮反复压缩。
- **同步摘要**：压缩由小模型同步完成，成功前不得替换当前上下文。新上下文由以下成分组成:
  - 重要事实摘要
  - 历史动作摘要
  - 当前正在进行的动作及工具结果
  - 最近若干条完整消息窗口
  同步压缩过程中始终保留当前用户请求、系统规则、引用来源和必要附件上下文。
  发生多次压缩时，小模型同时读取已有的重要事实摘要、历史动作摘要和当前未完成动作，根据事实与动作状态对摘要项执行保留、替换、新增或删除，禁止简单追加而累积重复、冲突或过期信息。
- **结构化状态保护**：任务列表、Planner 状态、当前计划步骤、完成概要、权限模式、文件变更和工具调用配对关系作为独立结构化会话状态原样保留，并在压缩后重新注入。摘要记录来源消息范围、版本和生成时间，避免多次摘要后无法追溯或旧摘要覆盖新状态。压缩不得打断进行中的工具调用，也不得留下孤立的 tool call 或 tool result。
- **长期记忆异步写入**：启用长期记忆时，压缩成功后将重要事实摘要异步写入长期记忆，不阻塞当前回答。写入任务携带 session、压缩版本、来源范围和幂等键，防止重复写入以及较旧任务覆盖较新摘要；未启用记忆时只更新当前会话的压缩状态。
- **失败与回退**：小模型超时、失败、返回空摘要或压缩结果仍超预算时，保留原工作上下文，不得用失败结果覆盖；随后采用安全的 token 滑动窗口继续执行，并向前端报告失败原因。只有完整的新上下文通过 token 预算和工具消息完整性校验后，才能原子替换旧上下文。
- **前端状态同步**：压缩期间通过 `compression_started` 显示独立的“正在压缩上下文”状态；完成、失败或取消时分别发送 `compression_applied`、`compression_failed`、`compression_cancelled`。完成事件携带压缩前后 token 数、窗口上限、摘要版本和保留消息范围，前端收到后立即更新上下文百分比。

##### 任务列表
任务列表用于管理复杂任务的长期进度, 属于当前会话，会跨消息保留，直到 Agent 主动结束任务列表。

任务列表有三个核心动作：创建列表、完成列表项、结束列表。创建后，系统会记录每个列表项的 ID，并标记当前正在处理的一项。Agent 完成某一项后必须写入完成概要，然后才能继续处理下一项。

每轮 Agent 启动时，后端都会把当前任务列表写入系统提示词。模型能看到列表状态、当前项、已完成项和完成概要，因此后续回复会继续围绕这份任务列表推进。只要任务列表存在，Agent 会进入具备工具调用能力的执行路径，避免长程任务被简单问答流程截断。

前端右侧栏只展示任务列表状态。Agent 工具更新任务列表后，后端通过流式事件把新状态推给前端，前端收到后自动勾选完成项并显示概要。工具不直接操作界面，界面只根据后端状态渲染。

任务列表和上下文压缩相互隔离。旧消息被压缩后，任务列表仍会保留当前项、完成概要和完成状态，Agent 下一轮仍能从会话状态中恢复任务进度。


#### 长期记忆/语义召回
采用 **RAG 检索增强生成**作为提取方式。底层数据分为以下类型：
- `会话摘要(session_summary)`：每轮异步摘要，记录对话要点。
- `会话事实(session_fact)`：从摘要中提取的结构化事实单元，由 MemoryResolver 裁决并维护 active/superseded/expired 状态。
- `重要事实摘要(important_fact_summary)`：ContextBuilder 内 compress 节点生成的跨会话重要事实。
- `知识切片(knowledge_chunk)`：知识库文件的语义切片。
- `自定义记忆(user_custom)`：用户手动写入的自定义记忆。
- `用户规则(user_rule)`：用户自定义的长期规则，不经过 RAG 检索，以系统提示词形式直接注入。

##### 语义召回

1. **向量召回** — 使用 ChromaDB 余弦距离检索，`vector_score = clamp(1.0 - distance)`。若 ChromaDB 不可用或返回零得分，回退到 SQLite 内嵌 JSON 向量的余弦相似度（归一化到 [0,1]）。

2. **关键词召回** — 从 query 提取英文 token + 中文 2~4 字子串，过停用词后以 SQL ILIKE 预筛出候选 doc，再用 Python 覆盖率 + 词频加权打分：每个词按长度加权（`weight = min(max(len, 2), 6) / 6`），出现次数加成（`+ min(occ-1, 2) * 0.08 * weight`），最终 `keyword_score = coverage_score + phrase_bonus`（phrase_bonus 为 `min(matched_terms, 4) * 0.03`）。

3. **合并去重** — 以 `memory_id` 为 key 去重。两路都命中的候选：`merged_score = 0.6 × max(v, k) + 0.4 × avg(v, k) + 0.05`（通道奖励）；仅一路命中：`merged_score = max(v, k)`。

4. **CrossEncoder ReRank** — 使用本地 CrossEncoder 模型 `BAAI/bge-reranker-v2-m3` 对 `(query, document)` 对做语义精排，原始 logit 通过 sigmoid 归一化到 [0,1]。未配置 ReRank 模型时回退到 merged_score + 通道数 + importance 排序。

5. **最终联合评分** — 对 ReRank 后的每条结果计算三维分数：
   $$
   relevance\_score = \max(rerank\_score, merged\_score)
   $$
   $$
   freshness\_score = \frac{1}{1 + age\_days / 30}
   $$
   $$
   final\_score = 0.5 \times relevance + 0.3 \times freshness + 0.2 \times authority
   $$
   权重来自配置项 `relevance_weight=0.5, freshness_weight=0.3, authority_weight=0.2`。

6. **阈值过滤** — `final_score < score_threshold` 的直接丢弃。阈值可配置，默认约 0.3。

7. **最终排序** — **以 `updated_at DESC（最新优先）为首要维度**，同等新度下按 `final_score DESC` → `current_session_match DESC` → `relevance DESC` → `importance DESC` 排列。理由是 score_threshold 已经过滤了无关内容，候选集内越新的信息越可能反映当前事实，而非 pure relevance。

8. **四层合并 & topK 截断** — `会话事实` / `重要事实摘要` / `会话摘要` / `自定义记忆` 四路记忆按 `memory_type` 独立执行上述 1~7 步，各自返回 topK（`rerank_top_k`，默认 5），再跨类型合并去重，按 final_score 截断总条数上限，最终注入系统提示词的检索上下文。

##### 信息时效性
每条记忆携带 `created_at` / `updated_at` / `valid_from` / `valid_until` 时间戳，以及 `fact_status: active | superseded | expired`。检索时在过滤层先排除 `expired` 和 `superseded` 条目；排序层内优先召回新内容。事实更新策略：
- 单值强排他事实：新值覆盖旧值，旧事实标记 superseded。
- 多值弱排他事实：新值追加并去重。
- 时序事实：到期自动失效，标记 expired。
- 程序定义事实（如项目规则配置）：以规则为准，LLM 的输出仅作为全新事实的补充。

#### Skill

Skill能力是从通用Agent走向专用Agent的关键。其设计如下：

- 所有的内置Skill默认统一存放在根目录的`resources/skills/`文件夹中，用户级Skill放在用户知识库目录下的`.agents/skills/`文件夹中。
- 统一兼容[OpenAI开放标准](https://developers.openai.com/api/docs/guides/tools-skills)作为主标准，兼容[Anthropic标准](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)扩展字段。
  - 用户可以将一个Codex或者Claude Code使用的Skill原封不动的搬运到`.agents/skills/`文件夹中,即可开始使用;也可以在设置-Skill页面中自行加入Skill.
- 目录结构：
  ```text
  skill-name/                 # 单个 Skill 的根目录
    SKILL.md                  # Skill 元信息与执行说明，必须存在
    scripts/                  # Skill 使用的脚本，可选
    references/               # Skill 按需读取的参考资料，可选
    assets/                   # Skill 使用的静态资源与模板，可选
  ```
- 用户级Skill按用户知识库隔离，**用户登录或知识库目录变更时**扫描Skill目录，读取元信息，建立索引。索引只作为本地路由数据使用，不把所有已启用Skill的索引信息全量注入主模型上下文。
- 对于非Simple思考模式下的每次用户输入，Agent决策前先进行本地候选召回：基于Skill的`name`、`description`、`keywords`、`triggers`等元信息做关键词/BM25式粗筛，只保留少量候选（默认不超过20个）交给`Skill路由器`。`Skill路由器`调用小模型从候选中返回针对当前询问场景适合的3个Skill；小模型不可用或返回异常时，使用本地候选分数兜底。随后只将命中的Skill正文（`SKILL.md`）注入本轮运行上下文（用户下一轮询问后从上下文中去除），Skill正文默认只对当前轮生效，下一轮重新路由。
- 主模型上下文只允许看到本轮候选Skill的简短摘要和已路由Skill的正文，不允许看到全量Skill注册表。用户级Skill正文按用户上下文注入，不能提升为不可覆盖的系统级规则。
- 配备有2个Agent工具：列出所有Skill；使用Skill（主动召唤`SKILL.md`正文）。


### 次要功能
#### 扫描器

扫描器用于把临时文件或网页资料转换为可编辑的 Markdown, 用户可以上传知识库支持的文件、拖入本地文件、输入公共网页地址或打开内置示例；任务进入单工作线程队列后持续记录阶段和进度，完成结果保存在当前知识库的 `.mw/scan/<scan_id>/`，历史记录、收藏、草稿和导出状态持久化到 SQLite。

扫描结果页同时保留原文件与 Markdown。未启用 OCR 时，图片和文档资源以本地引用形式保留；启用 OCR 时，默认打开结构化纯文本版本，并允许在 OCR / No OCR 之间切换。两种 Markdown 都可以继续编辑、复制和保存到知识库；OCR 版本导出为 `.md`，带原始图片资产的 No OCR 版本导出为包含 Markdown 与资源目录的 ZIP。删除扫描历史时会同步清理对应收藏和 `.mw/scan/<scan_id>/` 受管目录。

##### 扫描队列

扫描队列复用扫描器的持久化异步任务机制，以“等待扫描 / 扫描中 / 扫描完成”看板集中处理多个文件和网页。扫描完成列只显示当天结果，更早的完成记录进入历史页；完成卡片可以直接打开源文件、收藏、复制 Markdown、保存到知识库或导出。完成列还支持逐项批量保存 Markdown，以及把全部当天结果和资源合并为一个 ZIP 后统一导出。

##### OCR

扫描器中的 OCR 默认开启，调用与知识灌库、Agent 图片附件相同的 **PP-StructureV3 高质量流水线**。模型不会并行推理：全局一次只处理一张图片或一个 PDF 页面，避免扫描器、灌库和附件同时占用同一组 CPU 模型。

1. **文档预处理**：使用 `PP-LCNet_x1_0_doc_ori`、`UVDoc` 和 `PP-LCNet_x1_0_textline_ori` 完成页面方向、透视/弯曲和文字行方向校正。
2. **版面与阅读顺序**：`PP-DocLayout-L` 识别标题、正文、图片、表格、公式、页眉页脚等区域，`PP-DocBlockLayout` 辅助恢复复杂页面的块级阅读顺序。
3. **文字识别**：`PP-OCRv5_server_det` 与 `PP-OCRv5_server_rec` 负责中英文文字检测和识别，低于配置置信度的文字不会进入结果。
4. **表格结构**：表格分类器区分有线表格和无线表格，再分别使用 `SLANeXt_wired`、`SLANeXt_wireless` 与对应的单元格检测模型恢复行、列、合并单元格和 HTML 表格。
5. **公式识别**：`PP-FormulaNet_plus-M` 将公式区域转换为 LaTeX，并以 Markdown 块公式写入结果。图表解析和印章识别当前关闭，不下载对应模型。
6. **结果生成**：各版面块按页码和阅读顺序合并为 Markdown；表格保留 HTML 结构，公式保留 LaTeX。扫描器 OCR 草稿去除图片节点，但不会删除表格、公式或标题层级；知识灌库还会在 frontmatter 中保留块类型、坐标、页码、顺序和统计。

整套模型作为一个 `paddleocr` 受管模型组保存在 `runtime/models/paddleocr/`。开启 OCR 但模型不完整时，存储管理会显示“等待确认下载”；只有用户确认下载或启用自动下载后才会获取模型。旧的 Mobile 检测/识别完成标记不再视为完整，必须重新下载结构化流水线。


#### 内置浏览器

- 工作区提供独立页面与默认半屏的右侧边栏模式，共用浏览会话及联网设置中的代理。
- 点击图书馆 URL 或 Agent 回答中的 `[N]` 引用，会自动展开右侧浏览器并跳转到对应网页。

#### 知识图谱
知识图谱分为四类: 语义知识图谱,文件树图谱,图书馆结构图谱,双向链接图谱.
四类图谱依赖同一套**前端渲染**:
  - 语义图谱无根节点,实体和文档节点根据 d3-force 力导向布局自动散开
  - 实体节点按类型着色(person→粉色, organization→靛蓝, project→青色, concept→橙色 等)
  - 实体节点为实心球,文档节点为虚线空心球
  - 拖拽节点时暂时固定位置,松手后力布局重新演算
  - 文件树图谱(父子层级)与语义图谱(自由网状)通过前端按钮切换,共享同一个 Canvas 渲染器
  - 对于实体节点,连接了1条边的大小为基础大小,每多连接1条边,则实体节点大小增加基础大小的10%,最多500%,更多则大小固定.
  - 图谱默认为释放态(电荷小球物理排斥),可以进行定格.
##### 语义知识图谱
在多模态文件灌库的路径中,文档被解析为 Markdown 和结构化 frontmatter 后分成两路:一路切片进入向量库,另一路在后台构建语义知识图谱。图谱抽取采用**本地优先、章节增量、联网裁决**的模式:本地模型与确定性规则负责扫描正文、提出实体和关系候选,联网小模型只判断本地无法确定的少量候选,不会接收整篇文档。抽取结果最终持久化到 SQLite,前端通过 D3.js Canvas 实时渲染。

###### 工作原理

1. **文档级跳过**:系统使用统一的 `ingestion_hash` 判断结构化文档是否变化。已经成功抽取且指纹未变化的文档直接复用现有图谱,不运行本地模型,也不产生联网请求。只有用户显式强制重建、抽取器版本变化或提示词规则升级时才主动使对应缓存失效。
2. **章节级增量**:需要更新的文档继续按稳定的 `section_id` 拆分,并为每个章节计算正文哈希。章节缓存同时记录正文哈希、抽取器版本、规则版本和结果结构版本;未变化的章节直接复用原实体与关系,只处理新增或修改过的章节。因此修改一段文字不会重新抽取整篇文档。
3. **本地全文扫描**:变化章节首先交给本地小模型和确定性规则。本地阶段识别实体名称、类型、别名、关系类型、置信度和原文证据,并过滤目录、空段落、代码噪声、无效名称、重复候选以及无法在原文中定位证据的关系。全文始终留在本机。
4. **置信度分流**:本地高置信候选直接进入图谱,低置信且没有可靠证据的候选直接丢弃。只有实体边界冲突、关系类型不明确、别名是否同义等灰区候选才进入联网裁决。联网请求只包含候选名称、类型和能够证明该候选的最短原文片段,不包含完整章节或完整文档。
5. **联网失败降级**:联网裁决受低优先级任务队列、并发限制、超时、重试和熔断保护。接口不可用、余额不足或超时不会让整篇文档失败;系统保留已经通过本地验证的高置信结果,将灰区候选标记为待重试,后续只重试这些候选。
6. **分层实体去重**:实体先经过大小写、空白、标点和规范别名归一化,名称与类型完全一致时直接本地合并。跨章节和跨文档实体再使用本地 Embedding 检索相似候选:高相似且类型一致的候选自动合并,明显不相似的候选保持独立,只有相似度落在灰区时才交给联网小模型裁决。关系边随后统一重映射到规范实体名并清理自环与重复边。
7. **原子落库**:系统将文档节点、实体节点、带原文 `evidence` 的实体关系、程序生成的 `mentions` 边、章节缓存和抽取状态一起写入 SQLite。单个章节只有在新结果通过校验后才替换旧结果,中断或失败不会先删除仍然可用的图谱。

这种模式把联网模型从“全文抽取器”变成“疑难候选裁判”。正常的重复执行不会付费,小范围编辑只承担变化章节的本地计算成本,真正产生联网费用的只有少量语义灰区。

- **关系类型**: `defines`,`contains`,`depends_on`,`produces`,`consumes`,`calls`,`configures`,`mentions`,`related_to`。
- **实体类型**: `person`,`organization`,`project`,`module`,`class`,`function`,`file`,`concept`,`config`,`data`,`other`。

- **灌库模型**:
  抽取结果写入 `runtime/db/relation/agent_service.db` 五张表:
  - `knowledge_graph_nodes` — 全部节点(文档 + 实体)
  - `knowledge_graph_edges` — 全部边,分为两种:
    - **实体-实体边**:本地抽取器确认或联网模型裁决通过的语义关系,携带 `evidence`(原文短语)
    - **文档-实体边**:程序自动生成的 `mentions` 边,连接文档节点与该文档 section 中出现的所有实体,`weight` 由 entity confidence 决定
  - `knowledge_graph_section_cache` — 章节正文哈希、抽取器与规则版本、已确认结果和待重试灰区候选
  - `knowledge_graph_dedup_decisions` — 已确认的实体对合并或保持独立判定,避免重复联网裁决
  - `knowledge_graph_document_status` — 每篇文档的抽取状态(completed/failed/skipped)
  图谱特点是**文档内通过有原文证据的语义关系进行关联,不同文档通过共享实体节点间接连接**,形成隐式的跨文档语义网络。抽取时不凭空推断跨文档关系,保证每篇文档的证据独立性,同时共享实体节点在外图中自然实现桥接。
  重建时按统一的 `ingestion_hash` 和章节正文哈希增量执行,已完成且未变化的文档直接跳过,变化文档只重新处理变化章节。

- **语义去重**:系统提供文档内增量去重和库级去重,两者使用相同的本地分层策略。规范名称或明确别名匹配时直接合并;Embedding 高相似且类型一致时本地合并;低相似候选直接跳过;仅将相似度灰区中的候选名称、类型和最短证据交给联网小模型裁决。图谱面板的“去重”操作只扫描新增或尚未判定的候选簇,已确认的映射会被缓存,不会在每次运行时重复付费。

> **注**: 首次打开图谱页面时,语义图谱默认模式需要显式加载。

#### 任务队列

任务队列是用于并行处理独立 Agent 任务的可视化调度面板。Issue 看板分为“等待认领”“处理中”“等待确认”三列，并可切换到历史页面查看“已确认”和“已终止”的任务。

- 创建任务时可输入 Prompt、设置“极高 / 高 / 中 / 低 / 随便做”五档优先级（默认“中”），并通过拖拽或文件选择器附加多个文件。每个任务绑定独立的持久化 Agent 会话，不会打断其他正在运行的会话。
- 调度器优先认领高优先级任务，并在用户设置的最大并行数内由多个相互独立的 Agent 同时执行；最大并行数默认为 5。
- 看板会持续刷新任务状态并以动效展示跨列移动。卡片支持直接查看详情、删除尚未认领的任务、终止处理中任务，以及确认待确认任务。
- 处理中任务必须维护任务列表，卡片使用分段进度条同步展示列表完成进度。详情区域复用完整 Agent 页面组件，并以静默消息同步更新后台任务输出，不会反复清空和重新加载整段对话。
- 等待确认任务保留完整对话、最终回答、任务进度以及 Agent 页面中的环境与变更、任务列表和子 Agent 信息；用户可确认归档，或输入后续 Prompt 让任务携带原会话上下文重新进入队列。

#### TODO/待办系统 - 自动化定时任务

TODO 系统用于管理用户侧的独立待办事项，与 Agent 会话内的任务列表分离。普通待办用于记录人工事项；自动化任务是 TODO 的特殊分类，用于把一段 Agent 指令绑定到指定时间或循环计划上。

自动化任务创建后会同时生成一条关联 TODO，并把自动化定义持久化到 SQLite。定义内容包括任务提示词、下一次运行时间、时区、循环规则、权限模式、启用状态和最近运行结果。前端 TODO 侧边栏会展示自动化任务及其下一次运行时间。

后端启动时会创建自动化调度器。调度器定期扫描已启用且到期的自动化任务，通过数据库租约抢占任务，避免同一任务被重复执行。到点后，调度器会创建独立 Agent 会话，把自动化任务保存的提示词交给 Agent 执行，并记录本次运行的成功、失败、输出或错误。

自动化任务支持单次、每日、每周和每月循环。循环任务执行完成后会按任务时区计算并写入下一次运行时间；单次任务执行后不再安排下一次。当前实现会更新自动化运行记录和下一次运行时间，但不会把关联 TODO 自动勾选完成，也不会主动向前端推送实时刷新；前端需要重新拉取后才能看到最新状态。

Agent 也可以通过 `add_automation` 工具创建自动化任务。适合的场景包括定时提醒、周期性整理、按计划执行代码库维护命令等。涉及文件写入、提交、删除或联网操作的任务必须选择匹配的权限模式，否则到点执行时可能因权限不足或需要用户确认而中断。

#### Dashboard

Dashboard 将知识库规模、用户活动、RAG 质量和 Agent 资源消耗放在同一页中。数据来自当前用户的知识库、图书馆、会话轨迹和持久化统计记录。Agent 完成一次回复后，已经加载的 RAG、Token 和耗时数据会随之刷新。

##### RAG 质量

RAG 卡片显示填充率（fill rate）、平均相关性（avg relevance）和置信度（confidence）。设一次召回返回的记忆和知识条目数分别为 $m_i$、$k_i$，请求上限分别为 $M_i$、$K_i$，返回条目的最终相关性分数为 $q_{ij}\in[0,1]$，则该次召回的基础指标为：

$$
fill_i=\min\left(\frac{m_i+k_i}{M_i+K_i},1\right)\times100\%,\quad
relevance_i=\frac{1}{m_i+k_i}\sum_j q_{ij}\times100\%
$$

标准记忆与知识召回中的 confidence 与平均相关性取同一数值。对于由知识检索工具产生、没有完整结构化快照的记录，系统会根据实际返回条数、`top_k` 和结果中可提取的评分补齐指标；没有结果时相关性记为 0。

环形图展示当前 Session 内全部召回样本的累计均值。第 $t$ 次召回后，任一指标 $x$ 的展示值为：

$$
\bar{x}_t=\frac{1}{t}\sum_{i=1}^{t}x_i,\quad x\in\{fill,relevance,confidence\}
$$

历史曲线使用相同的累计口径，并可选择最近 5、10、20、50、100、200、500、1000 次或全部 RAG 记录。

##### Token 用量

Token 卡片只统计模型调用真实返回并已持久化的 usage，不把普通运行节点或文本长度估算混入用量。若服务商没有直接给出总量，则使用输入与输出之和进行归一化：

$$
u_i=\begin{cases}
total\_tokens_i,&total\_tokens_i>0\\
input\_tokens_i+output\_tokens_i,&\text{其他情况}
\end{cases}
$$

模型调用按当前配置分为大模型和小模型。对任一统计分组 $g$，某一模型层级 $p$ 的用量为：

$$
U_{g,p}=\sum_{i\in g}\mathbf{1}(tier_i=p)u_i,\quad p\in\{\text{large},\text{small}\}
$$

分组可以是固定时间桶、单次模型调用或 Session。时间刻度模式支持从 1 分钟到自然月的粒度以及最近 1 小时至 30 天的统计范围；调用模式可限制最近调用次数；Session 模式可按更新时间或 Token 总量排序。三种模式都可以在堆叠柱状图和曲线图之间切换。

##### 知识库规模

知识库概况分别统计当前知识库内的非目录文件数，以及递归遍历全部集锦后得到的图书馆图书数。文件按小写扩展名归类，没有扩展名的文件单独归入“无后缀”，环形图只展示数量最多的五类。

若前五类文件组成集合 $E_5$，图中某类扩展名 $e$ 的占比为：

$$
P(e)=\frac{N_e}{\sum_{j\in E_5}N_j}\times100\%,\quad e\in E_5
$$

因此该百分比表示一种文件类型在“已展示的前五类”中的构成，而不是它在全部文件中的绝对占比。

##### 每日活跃热力图

热力图以最近一年的贡献图展示用户每天在图书馆、文档、知识、Agent、任务和其他模块中的有效操作。每类操作有独立的每日计分上限；设事件 $e$ 的原始分值为 $s_e$，所属操作的每日上限为 $C_{a(e)}$，在它之前已经计入的同类分值为 $S_{a(e)}$，则本次实际计分为：

$$
a_e=\min\left(s_e,\max(C_{a(e)}-S_{a(e)},0)\right),\quad
A_{d,m}=\sum_{e\in(d,m)}a_e
$$

总览取同一天所有模块得分之和。每日得分依次按 0、1—3、4—7、8—12、13—18、19—27、28 以上映射为七档颜色，避免单一操作的高频重复把热力图完全占满。筛选模块后，页面同步计算统计期内的活跃值 $\sum_d A_{d,m}$、活跃天数、截至当天的连续活跃天数和单日峰值 $\max_d A_{d,m}$。

##### Agent 思考耗时

耗时卡片按时间顺序铺开不同 Session 中的 message，可以选择最近 5 至 1000 条或全部记录。存在节点耗时时，一次回复的总耗时和节点占比分别为：

$$
T_k=\frac{1}{1000}\sum_n d_{k,n},\quad
R_{k,n}=\frac{d_{k,n}}{\sum_jd_{k,j}}\times100\%
$$

其中 $d_{k,n}$ 是第 $k$ 次回复中节点 $n$ 的 `duration_ms`。没有节点耗时时，系统优先使用用户消息与最终回复的时间差；时间戳也不完整时，才按轨迹数、工具数和输出长度估算：

$$
\widehat{T}_k=\max\left(0.8,\ 0.45N_{trace}+0.35N_{tool}+\frac{\widehat{N}_{token}}{25}\right),\quad
\widehat{N}_{token}=\left\lceil\frac{N_{char}}{4}\right\rceil
$$

估算值会明确标记为 `est.`。点击折线上的一次回复，可以查看对应 Session、用户问题、总耗时，以及各执行节点的耗时柱状图和玫瑰图占比；卡片顶部同时给出当前范围内的平均耗时和最大耗时。

#### Git版本管理

系统配备Git管理的功能,主要包括:

1. 在当前知识库根目录创建和管理独立 Git 仓库。
2. 从左侧图标栏或顶部栏打开 Git 边栏,分别显示在左侧或右侧。
3. 查看“更改”和“未进行版本管理的文件”,并按文件勾选要提交或回滚的内容。
4. 在文件树和资源管理器中显示 Git 状态颜色,文件夹会继承内部变更颜色。
5. 在固定底栏填写提交概要,复用历史提交摘要,并切换本地分支。
6. 提交选中文件,或提交后进入推送弹窗。
7. 推送前确认本地分支、远程仓库、远程分支、未推送提交和涉及文件,也可以新建推送目标。
8. 回滚、切换分支和拉取更新时,自动失效对应文件的灌库索引与图谱索引,并清理旧切片、旧图谱节点和边。
9. Agent 配备Git管理工具, 可使用同一套 Git 能力读取状态、查看差异、提交、推送、回滚、建分支、切分支、拉取和添加远程仓库。

#### Markdown-to-HTML

用户可以从文件右键菜单或独立的 Markdown-to-HTML 页面发起 HTML 可视化。对文件树或文件资源管理器中的文件选择“HTML 可视化”后，系统会先完成该文档的灌库处理，再打开 HTML 可视化页面、收起文件树并展开 Agent 侧栏创建任务。多模态文档使用 Markdown 中间层生成页面，不直接依赖原始格式或解析 JSON。

页面提供“原结构”和“AI 提炼”两种模式。原结构模式沿用文档原有层级，AI 提炼模式由 Agent 整理内容后生成页面；用户还可以选择强动效、阴影、圆角和 emoji 等生成选项。任务执行期间会显示进度，生成结果通过“展示 Markdown-HTML”工具挂载到前端。

生成中的 HTML 保存在 `runtime/visualizations/`。完成后可以保存到知识库的 `{user_id}_html/`，也可以打开系统资源管理器选择其他位置。

#### 联合搜索

全库联合搜索在同一个搜索页中检索**文件库、图书馆、组件库和文献库**。标题搜索始终执行；“内容搜索”和“语义搜索”由用户分别开启。搜索框下拉菜单可以多选四个来源库，后端只访问被选中的库，且至少保留一个来源。

| 搜索方式 | 文件库 | 图书馆 | 组件库 | 文献库 |
|---|---|---|---|---|
| 标题搜索 | 文件名 | 图书或集锦显示标题 | 组件标题 | 文献标题；标题为空时使用附件文件名 |
| 全内容部分匹配 | 已解析正文索引与可直接读取的磁盘文本 | 描述、标签、来源信息；本地图书同时复用真实文件正文命中 | 固定分类与完整 Vue/HTML 源码 | 文献表标题与该行全部文本单元格 |
| 全内容语义搜索 | 已灌库的 `knowledge_chunk` | 图书元数据语义索引；本地图书同时复用真实文件向量命中 | 标题、分类和完整源码切片 | 标题、表格字段和完整文献正文切片 |

`.mw/` 中的受管投影不会再次作为普通文件库结果出现。图书馆中的网页条目只搜索已经保存的标题、描述、标签和 URL，不会在搜索请求中临时抓取远程网页正文。

##### 语义搜索链路

- 文件库继续使用知识灌库生成的向量切片。
- 图书馆元数据、组件和文献行使用 `unified_search_chunk`，按“用户 + 当前活动知识库”隔离。
- 首次语义查询或内容发生变化时，系统按内容哈希增量建立或更新索引，并清理所选来源中已经删除的资源；未选中的库不会被扫描或清理。
- 查询依次经过 Embedding、ChromaDB 向量候选、关键词候选合并、去重和 CrossEncoder ReRank。语义模型或索引不可用时会返回明确错误，不会用普通字符串匹配伪装语义结果。
- 同一资源同时命中标题、全文和语义时只显示一条结果，并保留全部命中方式与最高相关度。

##### 搜索页面与结果交互

- 文件、图书、组件和文献分别使用蓝、黄、红、绿图标。大搜索框显示“图标 + 库名”，TopCommandBar 小搜索框仅显示图标；点击来源不会关闭下拉菜单。
- **统一样式**沿用纵向搜索结果：四库按后端相关度混排，每条右上角显示来源图标和库名，每页显示 20 条。
- **分裂样式**从上到下排列四个来源区域，分别复用文件资源管理器中图标、图书卡片、组件预览卡片和文献文件块；每个区域按批次显示更多结果。
- 两种样式共享同一份搜索响应，切换只改变展示，不重新请求后端。滑动指示条负责表现切换状态，稳定滚动条占位保证大搜索框的位置和宽度不发生变化。
- 两个搜索菜单会在侧栏开关、顶栏展开和窗口尺寸变化期间持续锚定在各自搜索框下方。
- 搜索请求执行期间复用智能表格表项的 `PixelLoader`，搜索结束或失败后由同一搜索状态统一收起。

##### 四库可编辑侧栏

点击搜索结果会在工作区现有的右侧编辑栏中打开对应资源，不离开搜索页：

- 文件复用 `EditorPane`；Markdown、文本、代码等可编辑格式可以直接修改并保存，PDF、图片等使用各自原生预览。
- 图书复用 `LibraryItemDialog`，可以修改标题、描述、标签、封面以及本地文本图书的真实内容。
- 组件复用 `ComponentLibraryDetail`，左侧实时预览，右侧使用 `CodeEditor` 修改并保存 Vue/HTML 源码。
- 文献搜索块本身不可展开；右侧侧栏可以在“字段明细”和“内容”之间切换，前者复用 `LiteratureEntryCard` 字段编辑器，后者复用文献阅读页同款 `EditorPane`。

四类编辑器共享同一个右上角关闭按钮和同一条宽度拖动手柄。移动端改为右侧悬浮卡片，并与文件、浏览器、Git、Agent、Todo 等移动侧栏保持单侧栏互斥。保存图书、组件或文献后只原位更新当前搜索结果，不触发新的搜索请求。

##### 接口

- REST：`GET /search`，参数包括 `user_id`、`query`、`sources`、`fulltext` 和 `semantic`。
- gRPC：`SearchAllLibraries`，使用与 REST 相同的来源和能力开关。
- 组件源码侧栏保存复用 `PATCH /component-library/components`，支持增量更新 `source`、`title` 或 `tag`。

#### 收藏

文件、图书馆条目、组件和会话支持后端持久化收藏；各页面顶栏可使用“我的收藏”筛选，左侧“收藏”页集中展示对应分类。

用户可以收藏文件/图书馆的条目,可以收藏组件,也可以收藏Agent会话.

#### 隐私

文件与图书馆条目支持后端持久化隐私标记。普通浏览和“我的收藏”默认不显示隐私文件或图书，只有点击“我的隐私”后才会显示；隐私清单尚未成功加载时也会保持隐藏。文件树、文件资源管理器和图书馆顶栏均可使用“我的隐私”筛选，文件树和资源管理器右键菜单可在“收藏”下方直接切换“隐私化”；资源管理器列表显示“隐私状态”，小/中/大图标与图书馆卡片/条形项可直接切换隐私状态。隐私内容不会显示图片、文字或来源封面，左侧“隐私”页仅汇总文件和图书馆两个分类。

#### 存储、模型与编译管理

“设置 → 存储管理”由四部分组成：知识库/运行时容量统计、模型管理、编译管理和存储路径。存储路径负责展示实际目录、大小和安全清理入口；模型与编译器的下载、加载和安装操作集中在各自管理区，不在路径树中重复出现。

模型管理覆盖本地 Qwen、Embedding、ReRank 和 PaddleOCR 结构化流水线。本地 Qwen 行明确展示其作为主模型/小模型回退及图片理解模型的用途、CPU 设备、仓库、下载与内存状态；存储路径树同步展示 `runtime/models/local-llm/` 和 `runtime/models/paddleocr/` 的真实占用。每个模型首行显示配置名称、磁盘大小、下载/加载状态、当前是否启用和操作入口；展开 PaddleOCR 项可以核对版面、Server OCR、表格、公式、文档预处理模型以及明确关闭的模块。Hugging Face 模型按仓库总字节和实际落盘字节显示真实百分比；PaddleOCR 无法提前获得整组总量时只显示实时落盘字节和当前阶段，不生成假百分比。

编译管理当前负责 LaTeX 环境。系统会明确显示编译器来自系统安装还是 MetaWeave 托管，并列出发行版、版本、位置、大小、文件数、latexmk 以及 pdfLaTeX/XeLaTeX/LuaLaTeX 的可用状态。没有 MiKTeX 时可以在此确认安装、查看下载或安装阶段、取消、失败重试；只有 MetaWeave 托管的运行时可以卸载。

SDK 管理负责 DSH 代码子 Agent 的 Windows Runtime。当前 Runtime 固定使用 DeepSeek Harness 提交 [`47f943859bef60e4160492346772ded9b24f765a`](https://github.com/deepseek-ai/deepseek-harness/commit/47f943859bef60e4160492346772ded9b24f765a)，机器可读锁位于 `resources/dsh/upstream.json`。SDK 只在锁定提交、MW 补丁、Cordis 配置、内置 Node 主版本或 Runtime版本变化时运行 `scripts/build_dsh_sdk.bat` 重新生产；生成的 ZIP与 manifest直接打入 `AgentService.exe`，不需要网上托管。

“基础设置 → 启用 DSH”默认关闭。关闭时主 Agent不能创建或继续 DSH coding agent；开启后，应用界面完成启动即在独立后台线程校验并懒解压 Runtime，不阻塞后端、页面或其他模型初始化。再次关闭只停止后续 DSH调度，不自动删除已安装 Runtime。

当前 Windows x64 内置 ZIP为 **66,008,168 bytes（约 63.0 MiB / 66.0 MB）**，首次使用时从 EXE资源懒解压，安装后为 **192,256,620 bytes（约 183.4 MiB / 192.3 MB）**。制品已经包含 Node 24、DSH 生产依赖、Web资源和 Job Object启动器，用户无需联网，也无需安装 Node、pnpm、Python、编译器或 DSH。缺少 ZIP或 manifest时，PyInstaller构建会直接失败。

## UI/UX
### 三端响应式布局

界面统一适配桌面端、平板端与移动端：桌面端保留完整工作区和多栏管理能力，平板端按可用宽度收拢次要操作，移动端切换为单栏与紧凑控件，避免内容截断和横向溢出。

全局支持亮色、暗色与跟随系统三种显示模式。主题由统一设置状态驱动，页面、卡片、编辑器、弹窗和状态组件共享同一组语义色与明暗变量，切换时无需重新加载页面。
